# III. СОТРУДНИЧЕСТВО

### К-27. Сотрудничество это человек плюс направление

**На экране:** человек 212 в карточке показан одной шапкой, а под ней три
строки сотрудничеств: Медиа, Automy, Synapt. Роли и суммы у них разные

**Сервер:** GET /api/sotrudnichestva?chelovek_id=212 отдаёт три элемента,
в каждом chelovek_id = 212 и своё napravlenie

**Число:** SELECT COUNT(1) FROM sotrudnichestva WHERE chelovek_id = 212
равно трём, числу строк на экране

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-28. Один человек клиент одного направления и лид другого одновременно

**На экране:** у клиентом А по Медиа роль клиент, стадия в работе,
по Synapt роль лид, стадия на согласовании. Оба видны сразу

**Сервер:** в ответе GET /api/sotrudnichestva?chelovek_id=212 у элемента Медиа
rol = 'klient', у элемента Synapt rol = 'lid'. Запросы на смену одного
не трогают другой: PATCH сотрудничества Медиа отдаёт 200, у Synapt роль
в базе прежний

**Число:** SELECT napravlenie, rol FROM sotrudnichestva
WHERE chelovek_id = 212 отдаёт разные статусы по разным направлениям,
столько же строк, сколько на экране

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-29. Сотрудничеств по одному направлению может быть больше одного

**На экране:** у человека 212 две строки по Медиа: заказ 2025 года
и заказ 2026 года, у каждой свои проекты и своя сумма

**Сервер:** POST /api/sotrudnichestva с chelovek_id = 212
и napravlenie = 'media' при уже существующем таком сотрудничестве
отдаёт 201, а не 409

**Число:** SELECT COUNT(1) FROM sotrudnichestva WHERE chelovek_id = 212
AND napravlenie = 'media' равно 2. В схеме нет UNIQUE по паре
(chelovek_id, napravlenie): SELECT sql FROM sqlite_master
WHERE nazvanie = 'sotrudnichestva' этого ограничения не содержит

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-30. Поля сотрудничества: ровно те, что в схеме

**На экране:** в сотрудничестве поля направление, роль, стадия, контекст,
источник, кто порекомендовал. У реферала добавляются процент, выплаченное,
номер договора, ссылка на договор. Поля «ответственный» среди них нет

**Сервер:** GET /api/sotrudnichestva/<id> отдаёт ключи из схемы плюс
считаемые приведено, заработано, к выплате. Ключа otvetstvennyj нет

**Число:** PRAGMA table_info(sotrudnichestva) не содержит колонки
otvetstvennyj и совпадает со схемой: 15 хранимых колонок, три считаемых
поля приходят в ответе, но в таблице их нет

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-31. Ответственного на сотрудничестве нет, он только в задаче

**На экране:** в карточке сотрудничества поля «ответственный» нет
ни для чтения, ни для правки. Вместо него строка, собранная из задач:
«задачи ведут редактор А и участник Д»

**Сервер:** PATCH /api/sotrudnichestva/<id> с ключом otvetstvennyj отдаёт
400 с текстом про неизвестное поле, а не 200

**Число:** имена в строке «задачи ведут» равны результату
SELECT DISTINCT otvetstvennyj FROM zadachi WHERE id = <id>
AND status NOT IN ('sdelano','kogda_nibud'), то есть двум именам

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-32. Три роли плюс отдельный признак архива

**На экране:** в выпадающем списке роли ровно три значения: лид, клиент,
реферал. Архива в этом списке нет, он отдельной галочкой «в архиве»
Слова «партнёр» нет

**Сервер:** GET /api/spravochniki/roli отдаёт массив из трёх значений
PATCH сотрудничества с rol = 'partner' или 'v_arhive' отдаёт 400

**Число:** SELECT DISTINCT rol FROM sotrudnichestva даёт подмножество
из lid, klient, referal. Значения arhiv среди них нет

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-33. Пять стадий лида

**На экране:** у сотрудничества с ролью лид в списке стадий: не писали,
написали, на согласовании, ждём оплату, не сейчас. Ровно пять

**Сервер:** GET /api/spravochniki/stadii?status=lid отдаёт пять значений

**Число:** длина массива в ответе равна 5 и равна числу строк
в выпадающем списке на экране

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-34. Шесть стадий клиента

**На экране:** у сотрудничества с ролью клиент в списке стадий:
в работе, ждём оплату, на согласовании, ждём обратную связь, запланирован
зум, пауза. Ровно шесть

**Сервер:** GET /api/spravochniki/stadii?status=klient отдаёт шесть значений

**Число:** длина массива равна 6 и равна числу строк на экране

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-35. Стадия «ждём оплату» у лида это первая оплата

**На экране:** у лида стадия «ждём оплату» подписана как первая оплата,
у клиента та же стадия без этой пометки

**Сервер:** GET /api/spravochniki/stadii?status=lid отдаёт элемент
ждём оплату с пояснением «первая оплата»; тот же элемент
в ответе по роли клиент идёт без него

**Число:** строка на экране посимвольно равна полю pojasnenie в ответе, расхождение 0
знаков на 5 проверенных стадиях из 5

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-36. Свой стадию в набор этого направления виден только в нём

**На экране:** в сотрудничестве по Медиа добавил свою стадию «на паузе
до весны» с галочкой «добавить в набор». Открыл сотрудничество по Synapt,
в его списке этого статуса нет

**Сервер:** POST /api/spravochniki/statusy с napravlenie = 'media'
и oblast = 'napravlenie' отдаёт 201. GET /api/spravochniki/statusy?napravlenie=synapt
этого значения не содержит, GET с napravlenie=media содержит

**Число:** SELECT napravlenie FROM spravochnik_stadij WHERE nazvanie = 'на паузе
до весны' отдаёт ровно одну строку со значением 'media'

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-37. Свой стадию в набор всех направлений виден везде

**На экране:** добавил свою стадию с областью «все направления». Открыл
Synapt, Automy, Медиа, в каждом он в списке

**Сервер:** POST /api/spravochniki/statusy с oblast = 'vse' отдаёт 201
GET /api/spravochniki/statusy с любым napravlenie содержит это значение

**Число:** SELECT napravlenie FROM spravochnik_stadij по этому значению отдаёт
NULL в колонке направления, а число направлений, в чьём списке он виден,
равно восьми

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-38. Свой разовый статус живёт только в этой карточке

**На экране:** ввела свою стадию без галочки «добавить в набор». В этом
сотрудничестве она стоит. Открыла другое сотрудничество того же направления,
в списке её нет

**Сервер:** PATCH /api/sotrudnichestva/<id> со svoja_stadija = "своя стадия
текстом" и пустой stadija отдаёт 200, записи в справочник не создаёт
GET /api/spravochniki/stadii?napravlenie=media этого текста не содержит

**Число:** SELECT COUNT(1) FROM spravochnik_stadij WHERE nazvanie = <этот текст>
равно нулю, при этом SELECT svoja_stadija FROM sotrudnichestva WHERE id = <id>
этот текст отдаёт, а stadija у этой строки null

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-39. Последняя строка выпадающего списка это «своя стадия»

**На экране:** открыл список статусов, последняя строка «своя стадия»
Нажал, появилось поле ввода и галочка «добавить в набор»

**Сервер:** GET /api/spravochniki/statusy отдаёт массив, и элемент «свой
статус» в нём не лежит: это элемент интерфейса, а не значение справочника

**Число:** в ответе 5 значений справочника, в списке на экране 6 строк: пять стадий
плюс строка «своя стадия», разница ровно 1

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-40. Стадии не считают общение

**На экране:** поменял стадию с «написали» на «на согласовании». Поле
«дней без общения» в карточке не изменилось: оно считается из закрытых
задач и рассылок, а не из стадии

**Сервер:** PATCH /api/sotrudnichestva/<id> со сменой стадии отдаёт 200,
и в ответе поле dnej_bez_obshcheniya равно прежнему значению

**Число:** SELECT MAX(kogda) FROM zhurnal WHERE obekt = 'zadacha' AND pole = 'status' AND stalo = 'sdelano'
до смены стадии и после совпадают. Отдельной таблицы касаний в схеме нет:
PRAGMA spisok_tablic не содержит kasaniya

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-41. Дата последнего общения считается сама, отдельной сущности нет

**На экране:** закрыл задачу по человеку 212, в карточке «дней без общения»
стало 0, дата общения сегодняшняя. Руками это поле не правится, поля ввода
у него нет

**Сервер:** PATCH /api/zadachi/1428 со status = 'sdelano' отдаёт 200,
после него GET /api/ljudi/212 отдаёт dnej_bez_obshcheniya = 0

**Число:** SELECT MAX(kogda) FROM zhurnal WHERE obekt = 'zadacha' AND pole = 'status' AND stalo = 'sdelano'
равно сегодняшней дате и равно дате, показанной в карточке

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-42. «Не сейчас» это стадия лида, а не роль

**На экране:** в списке статусов значения «не сейчас» нет, в списке стадий
лида есть. Человек со стадией «не сейчас» остаётся лидом, не уходит в архив

**Сервер:** PATCH /api/sotrudnichestva/<id> со status = 'ne-sejchas' отдаёт
400, со stadija = 'ne-sejchas' при rol = 'lid' отдаёт 200

**Число:** SELECT rol, stadija FROM sotrudnichestva WHERE id = <id>
отдаёт rol = 'lid', stadija = 'ne-sejchas'. Строка остаётся в выборке
активных: COUNT по arhiv = 0 её включает

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-43. Настоящий конец это архив, а не «не сейчас»

**На экране:** лид со стадией «не сейчас» показывается в списке Людей
по умолчанию. Сотрудничество с галочкой архива по умолчанию скрыто

**Сервер:** GET /api/ljudi без фильтров содержит человека со стадией
«не сейчас» и не содержит человека с arhiv = 1

**Число:** SELECT COUNT(1) FROM sotrudnichestva WHERE stadija = 'ne_sejchas'
AND arhiv = 0 входит в счётчик «показано N из M» на экране, а COUNT
по arhiv = 1 в N не входит, только в M

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-44. Контекст, комментарий и особенности это три разных поля

**На экране:** в сотрудничестве три разных поля: контекст свободным текстом
про историю, комментарий к текущему статусу, особенности постоянным текстом
вроде «решения принимает только Дмитрий Владимирович». Поля подписаны
по-разному и лежат в разных местах карточки

**Сервер:** PATCH /api/sotrudnichestva/<id> с kontekst не затирает
kommentarij и osobennosti: GET после запроса отдаёт два прежних значения
неизменными

**Число:** SELECT kontekst, kommentarij, osobennosti FROM sotrudnichestva
WHERE id = <id> отдаёт три разных непустых значения, каждое совпадает
со своим полем на экране

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-45. Комментарий к статусу остаётся в истории после смены статуса

**На экране:** написала комментарий при роли лид, поменяла роль
на клиент. В секции «История событий» этого сотрудничества прежний
комментарий виден вместе со строкой смены статуса

**Сервер:** PATCH /api/sotrudnichestva/<id> со сменой статуса отдаёт 200,
GET /api/sotrudnichestva/<id>/istoriya содержит запись с полем
kommentarij, равным прежнему тексту

**Число:** SELECT COUNT(1) FROM zhurnal WHERE obekt = 'sotrudnichestvo'
AND obekt_id = <id> AND pole = 'status' равно числу строк смены статуса
в истории на экране

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое
