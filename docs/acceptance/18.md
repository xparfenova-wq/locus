# XVI. ОКР: ЦЕЛИ, РЕЗУЛЬТАТЫ, ЗАМЕРЫ

### К-135. Периоды календарные, Q4 это октябрь, ноябрь, декабрь

**На экране:** переключатель квартала показывает Q4 2026 и под ним
даты с 1 октября по 31 декабря

**Сервер:** GET /api/okr/celi отдаёт кварталы с календарными границами

**Число:** дата начала Q4 равна 2026-10-01, дата конца 2026-12-31

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-136. У цели от двух до пяти результатов

**На экране:** добавил шестой результат, появилась подсказка. Остался
с одним, цель помечена как неполная

**Сервер:** POST /api/okr/rezultaty шестым отдаёт 200 с полем podskazka

**Число:** SELECT cel_id, COUNT(1) FROM rezultaty GROUP BY cel_id показывает
значения от 2 до 5 на согласованных целях

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-137. При четвёртой цели направления появляется подсказка с текстом

**На экране:** создаю четвёртую цель для Медиа на квартал. Появился текст
«У Медиа на этот квартал уже три цели. Больше трёх редко доводят до конца
Точно добавляем четвёртую?» с кнопками «добавить» и «посмотреть текущие»

**Сервер:** POST /api/okr/celi четвёртой отдаёт 201 и поле podskazka
с этим текстом. Запрета нет

**Число:** число в тексте подсказки равно SELECT COUNT(1) FROM celi
WHERE napravlenie = 'media' AND period_id = '2026-q4' AND sostojanie = 'aktivna'

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-138. Цель имеет два состояния, в платёж идут принятые

**На экране:** создал цель, она помечена «черновик». В планёрке её нет
владелец нажал «принять», она появилась в планёрке

**Сервер:** POST /api/okr/celi создаёт с sostojanie = chernovik
GET /api/planerka?napravlenie=synapt не содержит черновиков

**Число:** число целей в планёрке равно SELECT COUNT(1) FROM celi
WHERE sostojanie = 'aktivna' AND period_id = текущий период

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-139. Активация цели без процедуры принятия

**На экране:** у цели состояния черновик, активна и архив. Кнопки «принять» и поля «кто принял» нет. Участник команды с доступом к направлению активирует цель одним действием

**Сервер:** PATCH /api/celi/{id} с актуальной versija и sostojanie = aktivna отдаёт 200 от участника с доступом к направлению. Присланное поле prinjal отдаёт 400 как неизвестное. Правило совпадает с К-784 и разделом ТЗ «Кто создаёт цели»

**Число:** `select count(*) from pragma_table_info('celi') where name in ('prinjal','prinjato_kogda')` равно 0

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-140. Источников замера ровно три

**На экране:** при создании числового результата выбор источника показывает три
значения: формула из данных Локуса, замер из подключённого аккаунта, ручной замер

**Сервер:** GET /api/spravochniki/istochniki_zamera отдаёт массив из трёх

**Число:** `SELECT DISTINCT istochnik FROM rezultaty` даёт не больше трёх значений

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

**Почему три, а не два:** подписчики, охваты и позиции приходят автоматически
из привязанных аккаунтов. Это не формула по базе Локуса и не ручной ввод
В базе уже 10 312 снимков публикаций и 349 снимков аккаунтов

### К-141. Источника «сумма целевых чисел задач» не существует

**На экране:** закрыл задачу с целевым числом 500, привязанную к результату
«1000 контактов». Число результата не изменилось

**Сервер:** PATCH /api/zadachi/1428 со статусом sdelano не меняет fakt
у связанного результата

**Число:** SELECT znachenie FROM zamery WHERE rezultat_id = 1 ORDER BY data DESC LIMIT 1 до и после закрытия
задачи одинаков

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-142. Целевое число задачи это план, а не замер

**На экране:** целевое число видно в карточке задачи рядом с названием,
подписано как план. В карточке цели оно не суммируется

**Сервер:** GET /api/okr/rezultaty/X не содержит поля summa_zadach

**Число:** факт считается по формуле результата, а не по планам задач: при сумме планов
задач 500 и фактическом замере 310 ответ отдаёт 310, расхождение с 500 равно
190

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-143. Ручной замер это четыре обязательных поля

**На экране:** вписываю замер, форма требует значение, дату, откуда
и автоматически подставляет меня. Без «откуда» не сохраняется

**Сервер:** POST /api/okr/zamery без otkuda отдаёт 400

**Число:** SELECT COUNT(1) FROM zamery WHERE otkuda IS NULL OR kto IS NULL
равно нулю

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-144. Замеры копятся строками, видна история

**На экране:** у результата показан последний замер и ссылка на историю
замеров. В истории видно 430 от 15 октября и 890 от 19 октября

**Сервер:** GET /api/okr/rezultaty/X/zamery отдаёт массив, а не одно значение

**Число:** SELECT COUNT(1) FROM zamery WHERE rezultat_id = X больше единицы
после двух замеров

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-146. Замер старше двух недель подсвечивается

### К-147. Веха весит ноль или сто процентов

### К-150. При закрытии задачи по цели спрашивают про замер

### К-151. Система не считает «не хватает задач на 400»

**На экране:** в карточке цели нет строки с арифметикой из планов задач
Есть число открытых и закрытых задач по цели

**Сервер:** GET /api/okr/celi/9 отдаёт otkrytyh_zadach и zakrytyh_za_mesjac,
не отдаёт nehvataet

**Число:** открытых равно SELECT COUNT(1) FROM zadachi WHERE cel_id = 9
AND status NOT IN ('sdelano','kogda_nibud')

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое
