# XLVII. РАССЫЛКА, ЗАДАЧА И БАЗА

### К-806. Новая рассылка создаёт две задачи сразу, веб

**На экране:** администратор в разделе Рассылки жмёт Создать рассылку, вводит название Школы Москвы, целевое число 500, ведущий редактор А, направление Synapt, жмёт Сохранить. Страница рассылки открывается уже с блоком Задачи рассылки, в нём две строки: Собрать базу по школам и Отправить рассылку по школам. Ни одной задачи вручную не создавала

**Сервер:** POST /api/rassylki с телом {nazvanie: Школы Москвы, plan_chislo: 500, otvetstvennyj: nikita, napravlenie: synapt} отвечает 201 и объектом rassylka{id, nazvanie, plan_chislo, otvetstvennyj, napravlenie, id_zadach}, где id_zadach это массив ровно из двух идентификаторов. GET /api/rassylki/{id}/zadachi отдаёт две записи с полями id, nazvanie, shablon, rassylka_id, plan_chislo, otvetstvennyj, srok

**Число:** `select count(*) FROM zadachi where rassylka_id = {id}` отдаёт 2, ни 0, ни 1, ни 3. Повторный GET через минуту даёт то же число 2, задачи не дублируются

### К-807. Новая рассылка создаёт две задачи сразу, телефон

**На экране:** администратор с телефона открывает Рассылки, жмёт плюс, заполняет в один столбец название Школы Москвы и целевое число 500, жмёт Сохранить. Экран рассылки открывается, блок Задачи рассылки свёрнут в строку Задачи, 2, по тапу раскрывается и показывает обе задачи в столбик без горизонтальной прокрутки

**Сервер:** тот же POST /api/rassylki, тот же ответ. Мобильный клиент не делает отдельных POST /api/zadachi, в сетевой панели после Сохранить ровно один запрос на запись

**Число:** `select count(*) FROM zadachi where rassylka_id = {id}` отдаёт 2 после создания с телефона, столько же, сколько с веба. Ширина блока задач не превышает ширину экрана 390 px

### К-808. Названия и шаблоны двух порождённых задач заданы, не угаданы

**На экране:** в блоке Задачи рассылки первая задача называется Собрать базу по школам, у неё чип шаблона Собрать базу, вторая называется Отправить рассылку по школам, чип шаблона Отправить рассылку. Чип шаблона виден на карточке задачи, не только в режиме правки

**Сервер:** GET /api/rassylki/{id}/zadachi отдаёт у первой записи shablon: sobrat_bazu, у второй shablon: otpravit_rassylku. Поле shablon приходит строкой из фиксированного перечня, не свободным текстом

**Число:** select shablon FROM zadachi where rassylka_id = {id} ORDER BY shablon отдаёт ровно два значения sobrat_bazu и otpravit_rassylku, без null и без пустой строки

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-809. Целевое число переносится в обе задачи из рассылки

**На экране:** рассылка Школы Москвы с целевым 500. В задаче Собрать базу по школам поле Целевое число показывает 500, в задаче Отправить рассылку по школам тоже 500. администратор это целевое не вводила ни разу, только в рассылке

**Сервер:** GET /api/zadachi/{zadacha_id} отдаёт plan_chislo: 500 у обеих задач и rassylka_id, равный id рассылки. Поле plan_chislo число, не строка

**Число:** select distinct plan_chislo FROM zadachi where rassylka_id = {id} отдаёт одно значение 500

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-810. Обе задачи встают на того, кто ведёт рассылку

**На экране:** в рассылке Школы Москвы ведущий редактор А. В обеих задачах в поле Ответственный стоит редактор А, не администратор, которая создавала, и не пусто

**Сервер:** POST /api/rassylki с otvetstvennyj: nikita даёт у обеих задач в GET /api/rassylki/{id}/zadachi поле otvetstvennyj: nikita. Поле kto_sozdal при этом ksenia, это разные поля

**Число:** `select count(*) FROM zadachi where rassylka_id = {id} and otvetstvennyj = 'nikita'` отдаёт 2. `select count(*) FROM zadachi where rassylka_id = {id} and otvetstvennyj is null` отдаёт 0

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-811. Срок обеих задач конец текущего спринта

**На экране:** в обеих задачах поле Срок заполнено датой последнего дня текущего спринта, та же дата, что показана в шапке спринта. Поле не пустое и не сегодняшняя дата

**Сервер:** GET /api/rassylki/{id}/zadachi отдаёт srok у обеих задач, равный полю end_date из GET /api/sprinty/tekuschij

**Число:** select distinct srok FROM zadachi where rassylka_id = {id} отдаёт одну дату, и она совпадает с end_date текущего спринта до дня

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-812. Новая рассылка создаёт выборку в Людях с чипом и нулём

**На экране:** сразу после создания Школы Москвы администратор открывает Люди и видит в линейке чипов новый чип школы Москвы, 0. Ноль, потому что людей ещё не загружали. Чип стоит в линейке рядом с остальными, не в отдельном меню

**Сервер:** POST /api/rassylki отдаёт id рассылки. GET /api/rassylki/{id}/ljudi отдаёт пустой массив и chislo: 0: чип есть, людей в нём пока нет

**Число:** `select count(*) from rassylka_ljudi where rassylka_id = {id}` отдаёт 1. Поле count в ответе равно `select count(*) from rassylka_ljudi where rassylka_id = {id}`, то есть 0

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-813. Чип рассылки показывает число людей, не целевое число

**На экране:** в базу рассылки Школы Москвы участница Б залила 500 человек. Чип стал школы Москвы, 500. администратор меняет целевое число рассылки на 600, чип остаётся школы Москвы, 500, не 600. Чип считает фактических людей

**Сервер:** PATCH /api/rassylki/{id} с {plan_chislo: 600} отвечает 200, после чего GET /api/rassylki/{id}/ljudi отдаёт count: 500, а GET /api/rassylki/{id} отдаёт plan_chislo: 600. Это два независимых поля

**Число:** count на чипе равен `select count(*) from rassylka_ljudi where rassylka_id = {id}`, то есть 500, а не значению plan_chislo 600

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-814. Задача с типом рассылка спрашивает новая или существующая, веб

**На экране:** администратор создаёт задачу, в поле Тип выбирает рассылка. Под полем Тип появляется выбор из двух вариантов: Новая рассылка и К существующей. Пока ни один не выбран, кнопка Сохранить неактивна и рядом подпись, что нужно выбрать рассылку

**Сервер:** GET /api/zadachi/shablony отдаёт для типа rassylka флаг nuzhna_rassylka: true. POST /api/zadachi с tip: rassylka без полей vid_volny и rassylka_id отвечает 422 и {oshibka: nuzhna_rassylka, pole: rassylka_id}

**Число:** число задач с tip = rassylka и rassylka_id is null в базе равно 0: `select count(*) FROM zadachi where tip = 'rassylka' and rassylka_id is null` отдаёт 0 в любой момент

### К-815. Задача с типом рассылка спрашивает новая или существующая, телефон

**На экране:** с телефона после выбора типа рассылка открывается не выпадающий список, а шит снизу с двумя крупными кнопками Новая рассылка и К существующей, высотой не меньше 44 px. Шит закрывается свайпом вниз, и тогда тип рассылка остаётся выбранным, а выбор рассылки снова пустой, Сохранить неактивна

**Сервер:** тот же POST /api/zadachi и тот же отказ 422 nuzhna_rassylka при пустом rassylka_id. Клиент не отправляет запрос, пока выбор не сделан

**Число:** число запросов POST /api/zadachi при закрытии шита свайпом равно 0. После выбора и Сохранить равно 1

### К-816. Вариант Новая рассылка создаёт рассылку с тем же названием и чип

**На экране:** администратор создаёт задачу Отправить письмо преподавателям, тип рассылка, вариант Новая рассылка, целевое 180. После Сохранить в задаче появилась строка рассылка: Отправить письмо преподавателям, а в Людях чип Отправить письмо преподавателям, 0

**Сервер:** POST /api/zadachi с {nazvanie, tip: rassylka, vid_volny: novaja, plan_chislo: 180} отвечает 201 и zadacha{id, rassylka_id, plan_chislo}, где rassylka_id новый. GET /api/rassylki/{rassylka_id} отдаёт nazvanie, равный nazvanie задачи, и plan_chislo: 180

**Число:** `select count(*) from rassylki where nazvanie = 'Отправить письмо преподавателям'` отдаёт 1, `select count(*) from rassylka_ljudi where rassylka_id = {rassylka_id}` отдаёт 1

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-817. Вариант К существующей цепляет задачу, новую рассылку не создаёт

**На экране:** администратор создаёт задачу Второй круг по школам, тип рассылка, вариант К существующей, в поиске выбирает Школы Москвы. После Сохранить в задаче строка рассылка: Школы Москвы, в Людях нового чипа не появилось, по-прежнему один чип школы Москвы, 500

**Сервер:** POST /api/zadachi с {vid_volny: suschestvuet, rassylka_id: {id}} отвечает 201, GET /api/rassylki отдаёт то же число рассылок, что до запроса. Новой рассылки в ответе нет

**Число:** число рассылок до и после одинаковое: `select count(*) from rassylki` отдаёт N и N. `select count(*) FROM zadachi where rassylka_id = {id}` выросло с 2 до 3

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-818. Целевое число у задачи типа рассылка обязательно, отказ без него

**На экране:** администратор создаёт задачу, тип рассылка, вариант Новая рассылка, целевое число оставляет пустым, жмёт Сохранить. Задача не создалась, поле Целевое число подсвечено, под ним текст про то, что без числа непонятно, что считать выполнением. Остальные введённые значения в форме остались, заново вводить не нужно

**Сервер:** POST /api/zadachi с tip: rassylka и plan_chislo: null отвечает 422 и {oshibka: nuzhno_plan_chislo, pole: plan_chislo}, запись не создана

**Число:** `select count(*) FROM zadachi where nazvanie = '{название из формы}'` отдаёт 0 после отказа. `select count(*) FROM zadachi where tip = 'rassylka' and plan_chislo is null` отдаёт 0

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-819. Целевое число у рассылки обязательно, отказ без него

**На экране:** администратор создаёт рассылку, название ввела, целевое число не ввела, жмёт Сохранить. Рассылка не создалась, поле Целевое число подсвечено. Ни задач, ни чипа в Людях не появилось

**Сервер:** POST /api/rassylki с plan_chislo: null отвечает 422 {oshibka: nuzhno_plan_chislo, pole: plan_chislo}. Ни одной записи в rassylki, zadachi, ljudi не создано

**Число:** после отказа `select count(*) from rassylki where nazvanie = 'Школы Москвы'` отдаёт 0, `select count(*) FROM zadachi where sozdano > {момент попытки}` отдаёт 0

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-820. Целевое число принимает только целое больше нуля

**На экране:** администратор вводит в Целевое число значение 0, получает отказ. Вводит минус 10, отказ. Вводит 500,5, поле не принимает запятую. Вводит слово пятьсот, поле не принимает буквы. Вводит 500, Сохранить проходит

**Сервер:** POST /api/rassylki с plan_chislo: 0 и с plan_chislo: -10 отвечает 422 {oshibka: plan_nevernyj, pole: plan_chislo}. С plan_chislo: 500 отвечает 201

**Число:** `select count(*) from rassylka_plan where plan_soobshenij <= 0` отдаёт 0. Тип поля plan_chislo в схеме integer not null

### К-821. Целевое число у задачи типа рассылка то же поле, что у бизнесовых задач

**На экране:** администратор открывает рядом задачу Собрать базу по школам с целевым 500 и обычную бизнесовую задачу с целевым 12. Поле называется одинаково Целевое число, стоит на том же месте карточки, выглядит одинаково. Отдельного поля вроде Целевое число рассылки нет

**Сервер:** GET /api/zadachi/{id} у задачи типа рассылка и у обычной задачи отдаёт одно и то же имя поля plan_chislo. В схеме задачи нет второго поля plan_rassylki

**Число:** в ответе GET /api/zadachi/{id} ровно одно поле с целевым числом: количество ключей, оканчивающихся на plan_chislo, равно 1

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-822. Переход из задачи в рассылку, веб

**На экране:** редактор А открывает задачу Собрать базу по школам, под заголовком строка рассылка: Школы Москвы. Он жмёт на неё и попадает на страницу рассылки Школы Москвы. Руками в разделе Рассылки ничего не искал

**Сервер:** GET /api/zadachi/{zadacha_id} отдаёт rassylka_id и nazvanie_rassylki, клиенту хватает одного запроса, чтобы нарисовать строку. Переход открывает GET /api/rassylki/{rassylka_id}, который отвечает 200 и nazvanie Школы Москвы

**Число:** число кликов от задачи до рассылки равно 1. Ответ GET /api/zadachi/{zadacha_id} содержит непустые rassylka_id и nazvanie_rassylki у всех задач, у которых rassylka_id не null

### К-823. Переход из задачи в рассылку, телефон

**На экране:** с телефона в задаче строка рассылка: Школы Москвы стоит той же строкой под заголовком, не спрятана в меню из трёх точек. Тап по ней открывает рассылку, кнопка Назад возвращает в ту же задачу, а не в список задач

**Число:** число тапов от задачи до рассылки равно 1, от рассылки назад в ту же задачу 1. Высота области тапа по строке рассылки не меньше 44 px

### К-824. Переход из рассылки в обе задачи, веб

**Сервер:** GET /api/rassylki/{id}/zadachi отдаёт все задачи с этим rassylka_id, независимо от шаблона, с полями id, nazvanie, otvetstvennyj, status, shablon

### К-825. Переход из рассылки в обе задачи, телефон

**На экране:** с телефона блок Задачи рассылки показан как список карточек в столбик, в каждой название, ответственный и статус читаются без прокрутки вбок. Тап по карточке открывает задачу

**Сервер:** тот же GET /api/rassylki/{id}/zadachi, тот же набор полей. Отдельного урезанного мобильного ответа без otvetstvennyj или status нет

**Число:** число карточек равно числу задач в базе по этой рассылке. Горизонтальная прокрутка внутри блока на ширине 390 px отсутствует

### К-873. Статусы в рассылке ровно четыре и названы одинаково везде

**На экране:** в фильтре По статусу в рассылке и в столбце статуса одни и те же четыре значения: не писали, отправлено, ответил, отказался. Пятого значения нет, и в фильтре нет значения, которого нет в столбце

### К-874. Переход из базы в задачи рассылки за два шага, не больше

**На экране:** участница Б при нажатом чипе школы Москвы жмёт К рассылке, попадает в рассылку, видит блок Задачи рассылки. Два шага от базы до задач, промежуточных меню и поиска нет

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-875. Создание рассылки с телефона и с веба даёт одинаковые записи
