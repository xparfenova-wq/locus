# Критерии приёмки Локуса

Перенос `ТЗ-ЛОКУС.md` в проверки. Одно решение ТЗ, один критерий

Каждый критерий это ровно три проверки, иначе он не критерий:

```
На экране    что видно глазами
Сервер       какой запрос что отдаёт
Число        какое число в базе сходится с каким числом на экране
```

Нумерация сквозная, К-1 и далее

## Сквозное правило: две ширины

**Каждый критерий, у которого есть блок «На экране», проверяется дважды:
на 1440 и на 390 пикселях.** Это правило действует на все критерии
документа, даже если в тексте конкретного критерия про это не сказано

```
1440    десктоп, рабочая ширина
390     телефон, iPhone 14 и подобные
```

**Расхождением считается**

```
действие доступно на одном и недоступно на другом
данные видны на одном и скрыты на другом без кнопки
число на экране отличается
порядок элементов меняет смысл
```

**Расхождением не считается**

```
раскладка: колонки против одной колонки
способ показа фильтров: линейка против шторки
прокрутка вбок внутри блока
элемент под кнопкой «ещё», если кнопка видна
```

Критерии с пометкой «телефон» в заголовке описывают случаи, где поведение
действительно другое: камера, перетаскивание долгим нажатием, шторка

**Три формы блока «Две ширины», по типу критерия**

```
обе ширины одинаково   «проверяется на 1440 и на 390, поведение
                       одинаковое», плюс словами, что именно смотрим
                       на 390, если это не очевидно
одна ширина            «только 1440» или «только 390»: у критерия
                       с пометкой веб или телефон в заголовке
поведение отличается   блок описывает отличие словами, а не
                       утверждает одинаковость
```

У чисто серверного критерия, где блока «На экране» нет, блока «Две
ширины» тоже нет: проверять нечего. Утверждать одинаковость там, где
поведение разное по условию, нельзя: это ложная проверка

## Имена и числа

Имена таблиц и полей взяты из `СХЕМА-БАЗЫ.md`. Ручки API из раздела
«Ручки API: единый список» в ТЗ. Имён вне этих двух списков быть не должно

**Транслит применяется только к нашим именам:** таблицы, колонки,
значения перечислений, ручки API. Системные имена остаются как есть
и не переводятся

```
SQLite        sqlite_master, pragma_table_info, name, type
DOM           document, window, querySelectorAll, scrollWidth
CSS           font-display, overflow-x, backdrop-filter
оболочка      sort, jq, cat, grep
HTTP          GET, POST, PATCH, DELETE, content-type
```

Транслит системного имени делает проверку невыполнимой: `dokument` в браузере не существует

**Открытая задача это одно определение на весь документ**

```
открытая    status NOT IN ('sdelano','kogda_nibud')
закрытая    status = 'sdelano'
отложенная  status = 'kogda_nibud': ни открытая, ни закрытая
```

«Когда-нибудь» в открытые не попадает: она не в работе и срока у неё
нет. Поэтому сравнение «status не равен sdelano» как определение
открытой неверно: оно затягивает отложенные. Дата закрытия отдельным полем не хранится,
она берётся из журнала: `select max(kogda) from zhurnal where obekt =
'zadacha' and obekt_id = ? and pole = 'status' and stalo = 'sdelano'`

**База это SQLite.** Все запросы в блоках Число написаны на её синтаксисе: `strftime` вместо date_trunc, `max` с несколькими
аргументами вместо greatest, `julianday` для разницы дат,
`date('now','-7 day')` вместо interval, `lower()` плюс `like` вместо
ilike. Отсутствие колонки проверяется через `pragma_table_info`,
отсутствие таблицы через `sqlite_master`, в обоих случаях ожидается
ноль строк с нужным именем

Числа в примерах сквозные: задача 1428, подзадача 1431, человек 212,
проект 64, цель 9, неделя 43, направление Медиа, база 1518 человек

# I. МОДЕЛЬ ДАННЫХ: ОСЬ И ЧЕЛОВЕК

### К-1. Ось «человек, сотрудничество, проект, задача» лежит в базе четырьмя таблицами

**На экране:** открыл человека 212, в нём секция Сотрудничества, в раскрытом
сотрудничестве проекты, в проекте 64 список задач. Ни один уровень

**Сервер:** GET /api/ljudi/212 отдаёт человека и массив сотрудничеств;
GET /api/sotrudnichestva/<id> отдаёт массив проектов; GET /api/proekty/64
отдаёт массив задач. Четыре разных адреса, не один вложенный ответ

**Число:** SELECT COUNT(1) FROM zadachi WHERE proekt_id = 64 равно числу
строк в списке задач проекта 64 на экране

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-2. Один человек, одна запись, компания это тот же человек

**На экране:** Глобал Дент и Светлана клиент А лежат в одном списке Людей,
одинаковыми строками. Отдельного раздела Компании в меню нет

**Сервер:** GET /api/ljudi?q=Глобал отдаёт запись с полем jurlico = true;
GET /api/ljudi?q=клиент А отдаёт запись с jurlico = false. Структура ответа
совпадает поле в поле

**Число:** SELECT COUNT(DISTINCT id) FROM ljudi равно счётчику «показано
N из M» в шапке Людей при снятых фильтрах

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-3. Признак юрлица это поле, а не отдельная схема

**На экране:** в карточке создания человека переключатель «компания или человек»
Переключил, набор полей не поменялся: те же имя, Телеграм, почта, телефон,
сайт, город, ниша, откуда пришёл, заметка

**Сервер:** POST /api/ljudi с jurlico = true и POST с jurlico = false
принимают одинаковый набор ключей, оба отдают 201

**Число:** PRAGMA table_info(ljudi) показывает одну таблицу, в ней колонка
jurlico типа INTEGER. Второй таблицы под компании в схеме нет

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-4. Поля человека: ровно те, что в схеме

**На экране:** в карточке человека 212 поля: имя, признак юрлица, город,
ниша, заметка, наш человек или внешний, активен, инициалы, цвет кружка,
онбординг, роль. Контакты отдельным блоком, они в своей таблице

**Сервер:** GET /api/ljudi/212 отдаёт ровно эти ключи плюс служебные id
и дату создания. Лишнего ключа в ответе нет

**Число:** список колонок PRAGMA table_info(ljudi) совпадает со списком
в схеме базы, раздел ljudi, по именам и по числу: 12 колонок вместе
со служебными

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-5. Контакт это список, а не одно поле

**На экране:** у человека 212 два Телеграма, личный и рабочий. Оба видны
строками, у одного стоит пометка «основной». Кнопка добавления даёт третью строку

**Сервер:** GET /api/ljudi/212/kontakty отдаёт массив, в каждом элементе
tip, znachenie, osnovnoj. POST туда же с tip = telegram добавляет строку,
не затирая прежнюю

**Число:** SELECT COUNT(1) FROM kontakty WHERE chelovek_id = 212 равно числу
строк контактов в карточке

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-6. Контакт привязывается к направлению

**На экране:** у клиента 212 в сотрудничестве по Медиа контактное лицо Алина,
в сотрудничестве по Automy контактное лицо Дмитрий. Открыл Медиа, видишь Алину,
Дмитрия не видишь

**Сервер:** GET /api/sotrudnichestva?chelovek_id=212 отдаёт два элемента,
в каждом своё поле kontakt_id. Значения разные

**Число:** SELECT kontakt_id FROM sotrudnichestva WHERE chelovek_id = 212
отдаёт две разные строки, они совпадают с двумя разными именами на экране

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-7. Пометка «основной» ровно у одного контакта на тип

**На экране:** поставил «основной» второму Телеграму, у первого пометка
снялась сама. Двух основных Телеграмов на экране не бывает

**Сервер:** PATCH /api/kontakty/<id> с osnovnoj = true снимает признак

**Число:** SELECT tip, COUNT(*) FROM kontakty WHERE chelovek_id = 212

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

# II. ЗАЩИТА ОТ ДУБЛЕЙ ВВОДОМ

### К-8. Уровень 1: совпало только имя, не показываем ничего

**На экране:** в базе десять Кать. Ввёл в поле имени «Катя», под полем

{"uroven": "net", "sovpadeniya": []} даже при десяти Катях в базе

**Число:** SELECT COUNT(1) FROM ljudi WHERE lower(imja) = 'катя' равно 10,
а число строк подсказки на экране равно нулю. Величина – пример рабочей базы, на тестовой не сверяется (отмечено 27.10)

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое

### К-9. Уровень 2: совпала фамилия, показываем список совпадений

**На экране:** ввёл фамилию «Семакин», под полем раскрылся список

**Число:** число элементов в массиве sovpadeniya равно числу строк

### К-10. Уровень 3: совпали имя и фамилия, меняется текст кнопки

**На экране:** ввёл «Семакин Игорь» целиком, список тот же, но кнопка создания

на единицу больше

**Две ширины:** проверяется на 1440 и на 390, поведение одинаковое
