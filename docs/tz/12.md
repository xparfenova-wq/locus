# ЧАСТЬ VI. КОНТРАКТ API

Пять дыр, найденных 17 октября, это отсутствие спецификации, а не баги реализации

## Жёсткие правила

**1. Правятся только переданные поля.** Правка имени не затирает телефон, почту и заметку
Раньше запрос перечислял все колонки и молча обнулял непереданные

**2. Справочники проверяются.** Направление и статус сверяются со списком, а не принимаются
любой строкой

**3. Чужой идентификатор не перезаписывает чужую карточку**

**4. Код 200 только при успехе.** На ошибке честный код ошибки

**5. Автор обязателен у всех записывающих вызовов**, иначе журнал недостоверен

### Вход для агентов

У каждого человека свой логин и пароль. У Клода каждого человека свой ключ, привязанный
к этому человеку

В журнале это видно: «редактор А закрыл задачу» или «Клод редактора А закрыл задачу»
Разница важна, когда разбираешь, откуда взялась запись

Технически это одна колонка в журнале: кто и чем. Делается сразу, потом добавить
сложнее

## API как главный вход

У всей команды есть Клод. Самый дешёвый массовый ввод это не форма, а «Клод, разбери
транскрипт зума и залей касания в Локус»

Поэтому API проектируется как главный вход, а интерфейс как один из клиентов:

- пакетная запись касаний и задач
- ключ повтора: залил тот же транскрипт дважды, дубли не появились
- понятная инструкция для Клода каждого в команде

Это закрывает и импорт-экспорт, и проблему ввода
