### Где показывается панель людей

Решение 21 октября: третий уровень меню не везде. Он фильтр, и живёт только там,
где есть что фильтровать по человеку:

```
есть      Моё пространство, Задачи, Люди
нет       Планёрка, Полезное, ОКР, Направления, Проект, Кабинет, Поиск
```

**Планёрка:** людей нет, она собирается по направлению за спринт. Остаются
направления и период справа от них

**Полезное:** нет ни людей, ни направлений. Внутри свои вкладки (лента,
рефлексия, принципы, команда, график, новое), фильтры поверх них лишние
В рефлексии период стоит над вкладками, потому что она идёт по спринтам


## Архитектурные требования

Модули, данные и общие компоненты разделены по ответственности. Изменение одного экрана не должно нарушать стили или поведение другого. Показатели клиентов, задач и платежей используют единые предметные определения во всех разделах.

## Главное правило, из которого следует всё остальное

**У каждого поля должно быть понятно, кто и когда его заполняет**

Путей три:

```
система сама          считается из данных, человек не трогает
человек в момент      вводит тогда, когда и так делает это действие
человек через Клода   надиктовал или скинул, Клод разложил по полям
```

Поля, на которые нет ответа «кто и когда», не заводим

Участник может заполнять данные через авторизованного AI-помощника. Ответственность за полноту и подтверждение результата остаётся у участника. Для каждого поля должен быть определён источник и момент заполнения.

Новые поля добавляются только при определённом источнике, владельце и проверяемой пользе. Неподтверждённые или отсутствующие данные не подменяются нулём.

Отсюда второе правило: **за каждый ручной ввод система отдаёт что-то видимое сразу**.
Закрыл задачу по человеку, увидел, как он ушёл из списка «без активных задач»
Поставил стадию «не сейчас», увидел созданную задачу

# ЧАСТЬ II. МОДЕЛЬ ДАННЫХ

## Ось

```
Человек
  └─ Сотрудничество (человек плюс направление)
       └─ Проект
            └─ Задача
```

## 1. Человек

Один человек, одна запись. Компания это тот же человек с признаком «юрлицо»: схема одна,
Global Dent лежит рядом со Светланой клиентом А

Свои поля человека: имя, признак юрлица, город, ниша, заметка, кто он в базе
(сам человек или контактное лицо клиента), архив с датой

**Контактов среди полей человека нет.** Телеграм, почта, телефон и сайт лежат
отдельным списком: у человека бывает личный Телеграм и рабочая почта, одним
полем это не хранится. Строка списка: тип, значение, пометка «основной»,
порядок

Контактное лицо привязывается к направлению: у клиента бывает своё лицо
по медиа и своё по бухгалтерии

**Поля «откуда пришёл» у человека нет.** Кто привёл, видно из сотрудничества
реферала: у него перечислены приведённые клиенты. Отдельное текстовое поле
дублировало бы эту связь и расходилось бы с ней

### Откуда человек попадает в базу

Четыре входа, других нет:

```
Люди, кнопка «+ человек»     главный путь, кнопка в шапке раздела
из задачи                    поле «клиент», последняя строка
                             «создать нового»
из проекта                   то же в поле клиента
из рассылки                  загрузка базы файлом, сразу пачкой
```

**Через поиск человек не создаётся.** Поиск ищет, а не заводит: иначе
опечатка в поиске рождает дубль

**Форма одна и та же** во всех случаях. Открывается попапом, не отдельной
страницей: человека заводят по ходу другой работы, уводить с экрана нельзя

**Что подставляется из контекста**

```
из задачи Synapt      направление Synapt, роль лид
из проекта            клиент этого проекта
из Людей              ничего, выбираешь сама
```

### Защита от дублей вводом, а не чисткой

Причина: 80 групп дублей накопились потому, что завести вторую Катю дешевле,
чем найти первую

**Четыре уровня срабатывания, по строгости:**

```
совпало только имя            не показываем ничего
совпала фамилия               показываем список совпадений
совпали имя и фамилия         показываем список, меняем текст кнопки
совпал телефон или ник        жёсткая остановка, создать нельзя
```

При совпадении фамилии под полем ввода раскрывается список, максимум пять строк,
в каждой контекст, чтобы отличить:

```
Семакин Игорь     Наставничество, клиент, общались 2 дня назад
Семакин Игорь     Synapt, лид, не писали
```

Под списком две кнопки, и это развилка: мы нашли того, кого ты вводишь,
или это однофамилец

```
открыть Семакина Игоря        он уже есть, иду к нему
всё равно создать нового      это другой человек с тем же именем
```

**Сценарий целиком.** участница Б вводит «Семакин Игорь», чтобы создать карточку
и поставить задачу. Локус показывает, что такой уже есть. участница Б нажимает
«открыть Семакина Игоря», открывается его карточка, и сверху всплывает
подсказка:

```
Вы хотели создать Семакина Игоря, но он уже здесь

                  поставить задачу      закрыть
```

Нажала «поставить задачу», открылась карточка создания задачи с уже
подставленным человеком. Это основной сценарий: пришла заводить человека,
а на самом деле нужна задача по существующему

Нажала «всё равно создать нового», создаётся второй Семакин Игорь
В обеих карточках появляется строка «есть однофамилец», чтобы потом
не путаться

**Поля «есть однофамилец» нет.** Строка считается запросом при открытии
карточки: есть ли другой человек с тем же `imja_norm`. Хранить это полем
значило бы обновлять его у двоих при каждом переименовании

Совпадение по телефону и нику это не подсказка, а стоп: один номер
не бывает у двух людей. Создать нельзя, только открыть существующего
или изменить номер

**Нормализация перед сравнением**, иначе подсказка не срабатывает:

```
регистр               приводим к нижнему
ё → е                 Семёнов и Семенов это совпадение
пробелы               обрезаем по краям, двойные внутри сжимаем
телефон               только цифры, +7 и 8 в начале это один номер
ник                   без собачки, нижний регистр
```

Фамилия и имя разбираются по пробелу. Ввели одним словом, считаем фамилией

Автосклейка по одному имени запрещена: десять Кать это десять разных людей

## 2. Сотрудничество

Человек плюс направление. Один человек может быть клиентом медиа и лидом Synapt
одновременно, с разными стадиями и разными деньгами

Сотрудничеств по одному направлению может быть больше одного, но роли у них
разные: человек бывает клиентом Synapt и рефералом Synapt одновременно
**Два сотрудничества с одной ролью по одному направлению запрещены:** два
заказа в разные годы это два проекта внутри одного сотрудничества, а не два
сотрудничества. Уникальный ключ: человек плюс направление плюс роль

Поля:

```
направление
роль               lid, klient, referal
стадия             зависит от роли
arhiv              да или нет, отдельное поле, роль при этом сохраняется
контакт по направлению   ссылка на человека, если общаемся не с ним самим
контекст           свободный текст: что за история с этим человеком
комментарий        к текущей стадии, остаётся в истории после смены
особенности        постоянное: «решения принимает только Дмитрий Владимирович»
```

У роли реферал добавляются поля процента и договора, они описаны
в разделе про рефералов

**Вычисляемые поля**, в базе не хранятся:

```
последнее общение   дата последнего события по этому сотрудничеству
дней без общения    сколько прошло с этой даты
```

Событие это закрытая задача по человеку, смена стадии, отметка
общения руками, касание рассылки с отметкой «отправлено»
Ответ и отказ дату не двигают: это не наше действие

**Ответственного на сотрудничестве нет.** Он живёт только в задаче. Причина: если
на человеке нет задачи, ответственный ни за что не отвечает, это поле без последствий
В карточке показывается то, что следует из данных: «задачи ведут редактор А и участник Д»

### Роль отвечает «кто это»

```
лид        хотим, чтобы заплатил, пока не заплатил
клиент     заплатил или подписал
реферал    приводит клиентов за процент
```

**Архива среди ролей нет.** Это отдельное поле `arhiv`, при архивации
роль сохраняется. Подробно в разделе про архив

### Стадия отвечает «где в воронке»

Справочник стадий общий, какие доступны, определяет роль

Стадии лида:
```
не писали
написали
на согласовании
ждём оплату
не сейчас
```

Стадии клиента:
```
в работе
ждём оплату
на согласовании
ждём обратную связь
запланирован зум
пауза
```

Стадии реферала описаны в своём разделе: присматриваемся,
договариваемся, работаем, к выплате

**«Ждём оплату» у лида и у клиента это одна стадия справочника.**
Смысл задаёт роль: у лида это первая оплата, у клиента очередная

### Свои стадии

Везде говорим «стадия», слова «статус» у сотрудничества нет: статус есть
у задачи, стадия у сотрудничества

```
своя стадия в набор этого направления    видна только в нём
своя стадия в набор всех направлений     видна везде
своя разовая стадия                      только в этом сотрудничестве
```

В выпадающем списке последняя строка «своя стадия», поле ввода и галочка
«добавить в набор»

**Где это лежит.** Стадия из набора попадает в справочник стадий с кодом
вида `svoja_stadija_1`, и поле `stadija` ссылается на него как на обычную
Разовая в справочник не попадает: она лежит текстом в поле `svoja_stadija`
того самого сотрудничества, а `stadija` при этом пустая. Поэтому разовая
не появляется в фильтрах и в чужих карточках

**Стадии не считают общение.** Последняя задача и последнее общение – разные поля. Последняя задача обновляется при закрытии связанной задачи. Общение отмечает человек или бот: закрытая задача и отправленная рассылка сами по себе не доказывают живого разговора. Последнее общение общее по всем ролям человека, стадия его не меняет

Историческая статистика старой базы не задаёт правило новой системы: приоритет у решения администратора о разделении этих двух полей

**«Не сейчас» это стадия лида, не отдельная роль.** К отказникам возвращаются,
«не сейчас, давайте позже» это норма. Настоящий конец это архив

### Плашка «следующее касание»

Всплывает после действия, которое оставляет человека без следующего шага
Текст с вопросом, название задачи в кавычках и кликабельно, правится прямо здесь:

```
Создать задачу «Следующее касание по Игорю»?

[создать]  [не нужно]
```

**Когда всплывает и с каким сроком:**

```
стадия → не сейчас                    через месяц
стадия → любая другая                 конец следующей недели
роль лид → клиент                     конец этой недели
закрыл последнюю задачу по человеку   конец следующей недели
закрыл любую задачу по лиду           конец следующей недели
закрыл задачу «провести зум»          конец следующей недели
```

**Когда не всплывает:**

```
у человека уже есть открытая задача   незачем, шаг есть
поставили галочку архива              человека осознанно отложили
плашку закрыли по этому человеку      сутки тихо, иначе она раздражает
```

Не создал задачу, значит не вернёмся, значит место в архиве. Система подсказывает
именно это

### Направлений восемь

|---|---|

| Automy, AI-обучение и сопровождение бизнеса | есть |
| Automy Junior, AI для школьников и студентов | есть |

У направления признак «есть клиенты». У направления владелец клиентов и воронки нет: только
задачи, контент-план и показатели. Блоки воронки на таком направлении не показываются
вообще, а не висят пустыми

Направления лежат одной таблицей с признаком «активно или архив»

### Архив это признак, а не роль

Решение 23 октября после разбора. Была путаница: архив стоял и статусом,
и отдельным полем. Теперь однозначно

```
rol       lid, klient, referal     кем человек приходится
arhiv     да или нет               работаем сейчас или нет
```

Это **две независимые вещи**. Роль не теряется при архивации:

```
Игорь, Synapt     роль клиент, в архиве с 15 октября
```

Видно и кем он был, и что сейчас неактуален. Отдельное поле
`status_do_arhiva` больше не нужно: роль и так на месте

**Почему не статус «архив».** Если архив это четвёртая роль, то при
архивации прежняя затирается, и при возврате непонятно, кем человек был
Пришлось бы хранить её отдельно, то есть городить второе поле ради того,
что решается галочкой

**Что это даёт при возврате.** Снимаешь галочку, человек возвращается
со своей ролью. Спрашивать не нужно

```
Игорь вернулся из архива, роль клиент.  [отменить]
```

Роль можно поменять тут же, если он вернулся в другом качестве

### Два уровня архива: человек и сотрудничество

```
arhiv у человека          ушёл целиком, все его сотрудничества
                          перестают считаться

arhiv у сотрудничества    закрыли одно направление, по другим
                          работаем дальше
```

Человек в архиве, а сотрудничество нет: человек всё равно не считается
Верх перекрывает низ

**Зачем два уровня.** Клиент ушёл из Synapt, но остался в Медиа: архивируем
сотрудничество. Человек уволился и больше нигде не нужен: архивируем
человека, не перебирая его направления

### Архив сквозной: одна механика на все сущности

В архив уходят люди, сотрудничества, задачи, проекты, направления,
услуги, рассылки. Везде это признак «неактуально», не удаление

### Что делает архив

```
скрывает из списков по умолчанию
не считается в счётчиках текущего периода
убирает из меню (для направления)
```

**Архив датирован.** Даты есть и у ухода, и у возврата, иначе прошлые
недели не посчитать:

```
Игорь ушёл в архив 15 октября 2026, вернулся 23 октября

неделя 41, 5–11 октября     считается, был активен всю неделю
неделя 42, 12–18 октября    считается, был активен 12–15 октября
неделя 43, 19–25 октября    считается, вернулся 23 октября
```

**Как считается неделя.** Человек считается активным на неделе, если
он был не в архиве хотя бы один день этой недели. День ухода ещё
активный по К-1612, день возврата тоже активный. Человек и сотрудничество должны
иметь общий активный день: активность в разные дни одной недели
не считается совместной работой

Если Игорь ушёл 5 октября и вернулся 23 октября, неделя 42 целиком
архивная и не считается. Текущий возврат не меняет этот прошлый период

**История архивации хранится.** Уходил и возвращался несколько раз,
видны все отрезки:

```
15 октября ушёл, 23 октября вернулся
2 сентября ушёл, 9 сентября вернулся
```

Эта история лежит в журнале изменений, отдельной таблицы под неё нет

### Общение с архивным человеком не запрещено

Ничего не блокируется: можно писать, звонить, создавать задачу, вести проект
Архив это про отчётность, а не про запрет

### Выход из архива

Требование: **создала задачу на архивном человеке, он вернулся из архива. Без вопросов и диалогов**

```
создала задачу на архивном    задача создалась, человек вернулся,
                              роль прежняя
сняла галочку архива руками   человек вернулся, роль прежняя
```

Это не тихий возврат: у него есть причина, и она видна. На экране тост
«Игорь вернулся из архива: появилась задача», в ленте человека строка
с той же причиной, в журнале отметка, что архив снят из-за задачи

**Диалога «вернуть или оставить в архиве» нет.** Появилась работа,
значит человек снова в работе: спрашивать об этом каждый раз
означает добавить лишнее нажатие там, где ответ всегда один

**Роль не спрашивается ни в одном из двух случаев:** она сохранилась
при архивации. Если роль правда изменилась (был лидом, вернулся
рефералом), меняешь её в карточке обычным способом

**Хвост по закрытому сотрудничеству.** Бывает, что надо доделать
остаток, не возвращая человека в работу. Для этого задача ставится
не на человека, а на проект: у неё есть направление и проект, а поля
клиента нет. Такая задача архив не трогает

### Сквозной поиск по архиву

В поиске отдельная кнопка «искать в архиве». Это отдельная выдача,
не подмешивание к обычным результатам

## 3. Проект

**Автосоздание не дублирует.** Если по сотрудничеству уже есть проект,
при переходе в клиенты второй не создаётся

**Создаётся вручную у кого угодно, включая лида.** Если делаем бесплатный прототип
человеку, который ещё не клиент, проект нужен

**Создаётся автоматически** при переходе сотрудничества в клиентское, с именем
по умолчанию «имя клиента, направление». Это удобство, а не ограничение

Поля:

```
название
направление
сотрудничество     связь с человеком и направлением одновременно
статус             идёт, пауза, завершён. У проекта это статус,
                   а не стадия: стадия только у сотрудничества
кто ведёт          к кому идти с вопросами, не ответственность
контекст           описание работы
стоимость          общая сумма за весь проект
услуга             что именно продали, из справочника направления
```

**Дедлайна у проекта нет.** Сроки живут в задачах

Деньги привязываются к проекту

## 3а. Комментарии: три уровня

| Где | Что пишем | Пример |
|---|---|---|
| **Сотрудничество** | контекст отношений по направлению | «работаем с мая, платит вовремя» |
| **Проект** | контекст конкретной работы | «правки только через Алину» |
| **Задача** | обсуждение по ходу дела, нитью | «отправила, жду ответа» |

Путаницы нет: уровень виден по месту. Комментарий проекта показывается в проекте,
комментарий задачи в задаче


### Личных задач нет

Личные задачи не относятся к предметной области системы.

У задачи всегда есть направление. Записаться к врачу, купить подарок, сходить
в спортзал в Локусе не живут: для этого есть телефон и заметки

Почему это важно записать: без явного запрета кто-нибудь предложит «личное»
пятым типом задачи, и возражать будет нечем. Локус это общая карта работы,
а не личный планировщик. Как только в нём появляется личное, он перестаёт
быть общим: часть задач становится невидимой для команды, и картина перестаёт
быть полной
