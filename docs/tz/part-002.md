## 4. Задача

```
название               обязательно
описание               необязательно
направление            обязательно, подставляется из контекста экрана
тип                    клиентская, продуктовая, бизнесовая, внутренняя
это публикация         галочка внутри любого типа, раскрывает поля публикации
статус                 в плане, в процессе, на согласовании, сделано, когда-нибудь
спринт                 обязательно, это неделя
дата                   необязательно, любой день внутри спринта
ответственный          один
участники              сколько угодно
клиент                 обязательно для клиентских
проект                 обязательно для клиентских, если проект есть
целевое число          обязательно для бизнесовых
цель ОКР               необязательно
подзадачи              список
родительская задача    заполнено у подзадачи
комментарии            нить
```

**Направление обязательно у любой задачи.** Подставляется из контекста экрана,
а если из контекста непонятно, человек выбирает сам. Без направления задача
не сохраняется

### Спринт и дата

**Спринт** это неделя, общий горизонт. По умолчанию задача ставится до конца спринта

**Дата** это конкретный день внутри спринта, если он важен

### Направление подставляется из контекста

```
создаю из направления        направление подставлено
создаю из карточки клиента   подставлены клиент, направление, проект
создаю из проекта            подставлены проект, клиент, направление
создаю из общего экрана      направление выбираю вручную, обязательно
```

### Тип определяет обязательные поля

| Тип | Что требует |
|---|---|
| **клиентская** | клиент обязателен, проект, если по сотрудничеству он есть |
| **продуктовая** | работа над самим продуктом, а не рассказ о нём |
| **бизнесовая** | целевое число, кроме случая с галочкой «публикация» |
| **внутренняя** | ничего, кроме направления |

Тип отвечает на вопрос «зачем работа». Публикация отвечает на вопрос «в каком
виде результат», это другая ось, поэтому она не тип, а признак

**Граница между продуктовой и бизнесовой:** продуктовая это как мы качаем
продукт, бизнесовая это как мы о нём рассказываем и привлекаем. Пост в свой
канал бизнесовый, потому что работает на привлечение

Система не может проверить, верно ли выбран тип: это решение человека
Поэтому проверяется другое, и это надо знать при приёмке:

```
проверяется машиной     что все четыре типа есть
                        что каждый требует свои обязательные поля
                        что тип виден в карточке и фильтруется

не проверяется          правильно ли человек выбрал тип
```

Спорные случаи разбираются на планёрке и дописываются в принципы примерами,
а не правилами. Пример в принципах работает, правило нет

**У бизнесовой задачи с галочкой «публикация» целевое число не обязательно:**
охват подтянется сам после выхода и станет числом. Иначе люди будут вписывать
фальшивые числа, лишь бы сохранить задачу

### Публикация это признак, а не тип

Галочка «это публикация» живёт внутри любого типа. Поставил, раскрылись
дополнительные поля:

```
площадка        Telegram, Instagram, YouTube, сайт
дата выхода
формат          пост, рилс, карусель, сторис, видео
рубрика         экспертная, развлекательная, продающая, своя
аккаунт         чей канал
```

**Своя рубрика добавляется на трёх уровнях**, как и своя стадия:

```
только в этот пост
в набор этого направления
в набор всех направлений
```

После выхода подтягивается охват из замеров

**Что развязывает признак вместо типа:**

```
пост для клиента Медиалаба       клиентская + публикация
пост в канал Automy              бизнесовая + публикация
рассылка на 500 человек          бизнесовая + публикация
поздравление с днём рождения     внутренняя + публикация
разбор продукта внутри команды   продуктовая, публикации нет
```

**Как публикация считается в двух системах сразу:**

```
в планёрке        задача считается в блоке своего ТИПА
                  клиентская публикация идёт в блок Клиенты,
                  продуктовая в блок Продукт,
                  и дополнительно попадает в блок Контент

в ОКР             по целевому числу или привязке к цели, как любая задача
                  охват подтягивается как замер, если цель про охват

в контент-плане   все задачи с галочкой, независимо от типа

**Фильтры внутри контент-плана.** Решение администратора 23 октября: ребятам
из медиа нужно открыть день и увидеть только свои публикации, не перебирая
остальное. Фильтры по площадке, формату, рубрике, аккаунту, направлению
и ответственному. Значения собираются из самих задач, списка в коде нет

Фильтра по типу задач на общем списке задач нет и не будет: задачи
планируются на весь спринт, а не на конкретный день, и такой фильтр
там не отвечает ни на один вопрос
```

Блок Контент в планёрке это не отдельный учёт, а срез: те же задачи,
показанные со стороны публикаций. Задвоения в числах нет, потому что в сводке сверху считаются типы, а Контент показывает список

### Аккаунт

Аккаунт это конкретный канал, куда уходит публикация. Не площадка (Telegram),
а именно канал (@automy_ai). Нужен потому, что замеры охвата приходят по каналу,
и без привязки к каналу число не к чему прицепить

**Где живёт список аккаунтов:**

```
аккаунты направления   карточка направления, вкладка Аккаунты
аккаунты клиента       карточка клиента
```

В карточке направления заводится один раз:

```
Automy
  Telegram   @automy_ai
  Instagram  automy.ai
```

### Зачем правило выбора аккаунта

Человек выбирает аккаунт из списка. Вопрос только в том, какой список ему
показать: все аккаунты всех клиентов и всех направлений это десятки строк

**Правило одной фразой: список берётся оттуда, чей это канал**

```
работа для клиента      канал клиентский    → аккаунты клиента
работа наша             канал наш           → аккаунты направления
```

Разворачивается это так:

```
задача клиентская, клиент клиент А
→ показываем аккаунты клиентом А, пост идёт в её канал

задача не клиентская, направление Automy
→ показываем аккаунты Automy, пост идёт в наш канал

аккаунт на площадке один
→ подставился молча, выбирать нечего

аккаунтов несколько
→ выбор из них
```

**Где это живёт:** в карточке создания задачи, в поле «аккаунт», в момент,
когда поставлена галочка «публикация»

Аккаунтов нет вообще: поле пустое, рядом ссылка «добавить аккаунт», ведёт
в карточку направления или клиента. Создание задачи не блокируется:
публикацию можно запланировать до того, как канал создан

**Контент-план** это те же задачи с галочкой «публикация», показанные
**календарём месяца**. Видно месяц целиком, по дням, с публикациями в клетках

### Контент-план Медиалаба по всем направлениям

Медиа-команда ведёт соцсети каждого направления, поэтому контент-план
существует в двух видах:

```
/media/kontent      все направления разом, рабочий экран Медиалаба
/synapt/kontent     только Synapt
```

На экране Медиалаба над календарём линейка чипов направлений:

```
[все] [Synapt] [Automy] [Junior] [Медиа] [Драйв] [Платформа] [владелец] [Ассист+]
```

Несколько чипов разом: можно выбрать три направления. По умолчанию все
В клетке дня точки цветом направления, не площадки: на этом экране важнее,
чьё направление

**Клиентские публикации тоже здесь.** У них направление Медиа, а клиент виден
в карточке. Чипы направлений их не фильтруют, поэтому для них отдельная
линейка чипов клиентов, появляется только если клиентские публикации есть:

```
[все клиенты] [клиент А] [Ridges] [Таёжник] [Питер-культ]
```

Переключатель «только клиентские» и «только наши» над календарём

**Видно и запланированное, и вышедшее.** Это один календарь, состояние
различается заливкой точки:

```
контурная точка      запланировано
залитая точка        вышло
серая точка          отменено: задача помечена удалённой
```

**Почему удалённая публикация видна в календаре.** Удаление мягкое,
строка остаётся с признаком `udaleno`. В календаре она показывается
серой, потому что иначе в отчёте за месяц пропадёт факт отмены: было
запланировано 23, вышло 14, а куда ушли девять, непонятно. В списках
задач такая задача не показывается, как и все удалённые

Под календарём переключатель периода: месяц целиком, или только то,
что уже вышло, за любой период. Второй режим нужен для отчёта клиенту
и для планёрки: «что вышло за ноябрь» это список, а не календарь

**Сводная строка над календарём:**

```
Ноябрь: запланировано 23, вышло 14, охват 186 000
```

Охват суммируется только по вышедшим, у которых замер есть. Если замер
не у всех, рядом честно: «охват по 11 из 14»

### На телефоне тоже календарь

Сетка остаётся, меняется содержимое клетки:

```
клетка            53px при полях 8px
строка недели     48px
в клетке          число дня и до трёх точек цветом площадки
больше трёх       четвёртая точка со знаком плюс
статус            залитая точка вышло, контурная запланировано
```

Названий и картинок в клетке нет: в 53px они не читаются

**Под сеткой список выбранного дня:** дата, счётчик публикаций, карточки
с площадкой, форматом, рубрикой, охватом и превью 56px

Месяц всегда шесть строк, даже когда последняя пустая. Иначе список под ним
прыгает при переключении месяцев

Навигация: свайп между месяцами плюс видимые стрелки, потому что жест находят
не все

### Где искать внутренние задачи и бэклог

Фильтр по типу «внутренняя» и чип «когда-нибудь». Направление у них тоже есть,
поэтому они находятся через обычные фильтры

### Какого размера бывает задача

Обязательное ограничение длительности задачи не установлено. Оценка времени не является основанием запрещать создание или выполнение задачи.

Вместо правила ориентир, он живёт в принципах, а не в системе:

```
задача это то, что можно закрыть одним решением
не закрывается одним решением → у неё есть подзадачи
```

«Запустить курс» это задача с подзадачами, а не ошибка. Декомпозировать
заранее не обязательно: подзадачи добавляются, когда стало понятно, из чего
работа состоит

**Что система делает с крупными задачами.** Ничего не запрещает, но подсвечивает в планёрке:

```
задача открыта больше трёх недель без закрытых подзадач
→ строка «висит 3 недели, подзадач нет»
```

Это разговор, а не ошибка: может быть, задача ждёт клиента

### Подзадачи

**Подзадача это полноценная задача**, у которой заполнено поле «родительская
задача». Все те же поля, своя карточка, свой адрес, своя строка в списках
Не строка с названием, а самостоятельная единица

Глубина два уровня: у подзадачи кнопки «добавить подзадачу» нет. Три уровня
нельзя показать в списке, не сломав читаемость

**Создание.** Нажал «добавить подзадачу», поверх карточки родителя открылась
карточка создания. Родитель не закрывается, остаётся под ней

**Что наследуется от родителя:**

```
наследуется              не наследуется
направление              название
проект                   описание
клиент                   дата
ответственный            целевое число
спринт                   цель ОКР
тип                      участники
```

Любое наследованное поле правится: это предзаполнение, а не жёсткая связь
Поэтому «ответственный наследуется» и «у подзадачи свой ответственный»
не спорят: при создании он подставлен от родителя, дальше это её собственное поле и меняется независимо

**Закрытие окна подзадачи:**

```
ничего не введено, кроме наследованного
→ окно закрывается молча, говорить тут нечего

введено название
→ сохраняем молча, автосохранение, окно закрывается

введено что-то, кроме названия, названия нет
→ «Без названия задачу не сохранить. Закрыть и потерять?»
  [закрыть]  [вернуться]
```

Ругаемся только на отсутствие названия: это единственное поле, без которого
задача не существует

### Подзадачи видны тише задач

Главное в списке это задачи. Подзадачи не должны с ними соперничать

**Переключатель в настройках вида**, как в Linear:

```
показывать подзадачи       да или нет, по умолчанию да
скрывать выполненные       да или нет, по умолчанию да
```

```
раздел Задачи        подзадачи видны внутри карточки родителя
                     выполненные скрыты, видно «1 из 3»
                     переключателем можно показать все

карточка задачи      подзадачи списком внутри, это их место

планёрка             показываются, но свёрнуто: строка «+2 подзадачи»
                     под родителем, раскрывается кнопкой

Моё пространство     показываются как обычные задачи, если они на мне
                     потому что мне их делать
```

Исключение для чужого направления: подзадача, ушедшая в Медиа, в списке
задач Медиа показывается обычной задачей. Для Медиа она не подзадача,
а работа

**Закрытие.** Подзадача закрывается сама по себе, у неё свой ответственный
Если закрываешь родителя с незакрытой подзадачей, появляется примечание:
«одна подзадача не выполнена, точно закрываем?»

### Задача в одном направлении, исполнитель из другого

Самый частый сложный случай. Automy Junior запускает курс, нужны посты,
дизайн делает Медиа

**Решение:** Junior создаёт большую задачу, внутри подзадачу, у подзадачи
меняет направление на Медиа и ставит исполнителя из Медиа. Задача сразу
уходит в Медиа

Работает это потому, что у задачи два разных поля:

```
направление      чья это работа. У подзадачи может отличаться от родителя
ответственный    кто делает
```

**Где она видна и как:**

```
в Automy Junior   подзадачей внутри «Запуск курса», отступом
в Медиа           обычной задачей верхнего уровня, с плашкой родителя
```

Плашка родителя стоит над названием, кликабельна, уводит к родителю:

```
┌────────────────────────────────────────┐
│ Automy Junior, Запуск курса            │  ← кликабельно
│                                        │
│ Отрисовать баннеры для запуска         │
│ Медиа, участница Е, до 26 октября              │
└────────────────────────────────────────┘
```

**Что считается где.** Задача учитывается в том направлении, которое
у неё в поле «направление»:

```
планёрка Медиа            задача попадает сюда
планёрка Automy Junior    видна в составе родителя, своей строкой не считается
```

Иначе задача задвоится в сводных числах

**Как исполнитель узнаёт.** Три слоя защиты от того, что задачу поставили,
а человек не в курсе и создал себе такую же:

```
1. уведомление                приходит сразу, см. раздел Уведомления
2. список задач проекта       при создании видно, что уже есть
3. точка непрочитанного       на задаче, которую я ещё не открывал
```

**Точка непрочитанного** это не отдельный блок и не фильтр: задача лежит
в общем списке среди равных, просто помечена точкой, как непрочитанное
письмо. Точка гаснет при открытии

Отдельного блока «Поставили мне» нет специально: он делил бы задачи
на важные и остальные, а все задачи равны

**Список открытых задач проекта.** Угадывать похожесть по совпадению слов
нельзя: «Отрисовать баннеры для запуска» и «Отрисовать баннеры для рассылки»
совпадут, хотя это разные задачи, а «Баннеры к запуску» не совпадёт, хотя
это та же самая

Поэтому система ничего не угадывает, а показывает факт:

```
в проекте 7 открытых задач          ← свёрнуто, под полем названия
```

Нажал, раскрылся список. Человек видит, что уже есть, и решает сам

### Что такое просроченная задача

```
срок прошёл, статус не «сделано»     просрочено
```

Для повторяющейся: есть непокрытые прошедшие дни

### Участники и просрочка

**Если задача просрочена, а я только участник, у меня она не считается
просроченной, но отображается с пометкой «участник»**

### Карточка создания

Попап по центру, полный список полей сразу, ничего не свёрнуто. Поля, которые
подставились из контекста, показаны уже заполненными

Кнопка «использовать шаблон» вверху

**Что подставлено по умолчанию**

```
спринт           текущий
срок             конец текущего спринта
ответственный    я
направление      из контекста, откуда создаю
статус           в плане
```

Срок меняется одним нажатием, в том числе на дату из другого спринта
Пустым не остаётся: задача без срока не попадает в недельный вид

**Задача живёт, пока не закрыта.** Спринт кончился, задача не закрыта:
она тащится дальше и видна в текущем спринте. **Срок при этом прежний**,
автоматически не двигается

Сдвинуть срок можно двумя способами: поменять дату в карточке или нажать
«продлить на спринт» над списком просроченных

**Материалы прикладываются прямо здесь**: кнопка «добавить», файл
или ссылка. То же в открытой карточке задачи

### Удаление и архив

Задачу можно удалить. Удалённое попадает в общий архив, откуда восстанавливается

### Дневной список задач

В Задачах чип «день» открывает общий календарь. Выбранная дата живёт в data=ГГГГ-ММ-ДД ссылки, список и сводка читают один день. Обычные задачи показаны по сроку, повторяющиеся – по своему правилу и не раньше даты старта. Скрытый спринт не ограничивает выбранный день. Четыре частоты дают за неделю7/5/1/число выбранных дней. Будущую задачу можно открыть, поставить будущую отметку нельзя

Стрелки периода меняют выбранный день на соседний. Убрать дату и выбор спринта возвращают недельный вид. В дневном режиме «динамикой» заменяется списком, доска доступна. При ошибке чтения прежние день, адрес и строки сохраняются; сообщение рядом с фильтром предлагает повторить выбор, автоматического повторного запроса нет. Более поздний выбор дня побеждает запоздавший ответ

День карточки отдельно хранится в den= и не теряется при правке или перезагрузке. Открытие задачи из выбранного дня списка или доски показывает и отмечает именно этот день. Это та же задача с тем же номером, дневных копий не создаётся

### Проверка удаления и восстановления задачи

Подтверждение удаления показывает буквальное имя и точное число отметок из прочитанной карточки. Два варианта: сначала оставить, затем удалить задачу; обе кнопки на всю ширину, на телефоне лист снизу. Снимок версии не подменяется свежим перед запросом. Чужая правка даёт конфликт, не автоматический повтор удаления

До DELETE или POST vernut браузер сохраняет намерение по участнику и номеру задачи. Если ответ потерялся, явная проверка только читает текущее состояние, перезагрузка не повторяет запись. Закрытие вопроса не теряет карточку и ссылку. Чужое восстановление/удаление сохраняется до нового явного действия; принять текущее состояние можно после свежего чтения. При отказе браузерного хранилища запрос не отправляется

GET /api/zadachi/номер/korzina требует входа и отдаёт только id, nomer, nazvanie, napravlenie, versija, udaleno и otmetki с авторами. Он работает для действующей и удалённой задачи, не пишет, версия и отметки относятся к одному снимку. Неверный номер400, несуществующий404, иной метод405. Основная ссылка удалённой задачи по-прежнему410. Карточка читает проверочное состояние и показывает корзину без редактирования, прежние отметки и общую кнопку восстановления. Восстановление возвращает тот же id и номер, прежние отметки не переписываются

### Статусы задачи

```
в плане
в процессе
на согласовании
сделано
когда-нибудь     + необязательная строка «почему отложено»
```

У статуса «когда-нибудь» свой чип-фильтр. В недельный вид такие задачи не попадают никогда

### Повторяющиеся задачи

**Задача одна, она не множится.** В списке всегда одна строка «Разобрать
входящие», а не десять штук за десять дней

**Как это работает.** У задачи есть правило повторения и отметки по дням
Строка одна, отметок много:

```
задача            «Разобрать входящие», одна запись
правило           каждый будний день
отметки по дням   22 октября сделано, 23 октября сделано,
                  24 октября не отмечено
```

**Что видно на экране сегодня**

```
24 октября, четверг

Разобрать входящие          повтор, каждый будний    в плане
```

Нажала «сделано», отметка встала на сегодня. Задача **не исчезает
из списка**: завтра она снова будет здесь со статусом «в плане»

**Если вчера не отметила**

```
24 октября, четверг

Разобрать входящие          повтор    в плане
                            вчера не отмечено
```

Строка одна. Под ней серым: за какие дни нет отметки. Нажала «сделано»,
Локус спрашивает, за какой день:

```
Отметить «Разобрать входящие»

  [x] сегодня, 24 октября
  [ ] вчера, 23 октября
  [ ] вторник, 22 октября

          отметить            отмена
```

**Диалог всегда показывает все непокрытые дни**, галочками. При одном
пропуске это две строки, при пяти шесть. Сегодняшний день отмечен
по умолчанию

Отметила вчерашний, вчерашний пропуск закрылся. Не отметила, он остаётся
видным под строкой задачи

**Накопленные пропуски**

Если пропусков больше трёх, строка подсвечивается и показывает число:

```
Разобрать входящие          повтор    в плане
                            5 дней без отметки
```

Нажала на эту подпись, открылся список дней с галочками: можно закрыть
несколько разом или снять правило

**Что не происходит.** Задача не копируется, не переносится, не создаёт
новых строк. В списке она всегда одна

### Просрочка у повторяющейся

Требование: **попадает в просроченные, если не закрыта
за свой день**

```
24 октября, четверг

Разобрать входящие      повтор    просрочено
                        вчера не отмечено
```

Вчерашний день кончился, отметки за него нет, значит просрочено
Строка при этом остаётся одна: это та же задача, просто с открытым
вчерашним днём

**Сколько дней просрочено** видно подписью: «вчера не отмечено»,
«3 дня без отметки». Чем больше пропусков, тем заметнее

**Кнопка «продлить на спринт» её не трогает.** Продлевать нечего:
у повторяющейся нет срока, который можно сдвинуть. Закрыть пропуск
можно только отметкой за конкретный день

**Срока и спринта у повторяющейся нет.** Поля срока и спринта при
включении повторения скрываются: срок это «сделать до такого-то числа»,
а повторяющаяся делается каждый день. Просрочка считается по дням
без отметки

Правило «спринт у задачи обязателен» на повторяющиеся не распространяется:
они видны в любом спринте

**В недельном виде** повторяющаяся задача видна всегда, в любом спринте
Переключение спринта её не прячет: она не привязана к неделе

**В итогах дня** она появляется, если отмечена сегодня, как любая
закрытая задача

### Поля повторения у задачи

```
povtorjaetsja     да или нет
chastota          kazhdyj_den, budnie, raz_v_nedelju, vybrannye_dni
dni               если vybrannye_dni: [1,3,5], понедельник первый
den_nedeli        если raz_v_nedelju: 2 это вторник
```

Поля другого правила не принимаются: непустой dni допустим только при
vybrannye_dni, den_nedeli только при raz_v_nedelju. При смене частоты
сервер очищает настройки прежнего правила. Неверный запрос отклоняется
целиком до записи задачи и журнала

При выключенном повторении непустые chastota, dni и den_nedeli не записываются: и создание, и правка обычной задачи отклоняют такой запрос

### Отметки по дням

Отдельная таблица: задача, дата, статус, кто отметил

```
otmetki_povtora
   zadacha_id
   data           день, за который отметка
   status         sdelano или propushcheno
   kto            ссылка на ljudi
   kogda          время отметки
```

История отметок показывает дату, сделано или пропущено и имя того,
кто отметил. GET задачи и GET её отметок отдают kto_imja вместе с kto;
имя читается из карточки участника, ссылка kto в прежней отметке не меняется при смене ответственного. На экране имя выводится буквальным
текстом, длинное переносится внутри строки истории

Строка появляется только когда человек что-то сделал с днём: отметил
сделанным или отметил пропущенным. **Несделанный день это отсутствие
строки**, строк на каждый несделанный день не заводим

У статуса два значения, и они про разное:

```
sdelano        задачу за этот день сделали
propushcheno   задача за этот день не нужна, и это осознанно:
               день закрыт, в просрочку не идёт
нет строки     день открыт, если прошёл значит просрочен
```

Зачем нужен `propushcheno`: без него день, когда задача не нужна,
навсегда остаётся просроченным и копится в подписи «5 дней без
отметки». Отличие от `sdelano` в том, что в статистику «делали
18 дней из 22» пропущенный день не идёт

**Почему отдельная таблица, а не поле у задачи.** Нужна история: видно,
в какие дни делали, в какие нет. По ней же считается статистика
«делали 18 дней из 22»

**Статус повторяющейся вычисляется, а не хранится.** Человек ставит
отметку за день, статус задачи складывается из отметок:

```
есть отметка за сегодня                     сделано
отметки за сегодня нет, прошлые закрыты     в плане
есть непокрытые прошедшие дни               просрочено
```

Завтра наступило, отметки за завтра нет, задача снова «в плане»
Так она каждый день на месте

Отметку ставит человек. «В плане» и «просрочено» это отображение,
а не записанный кем-то статус

### Выключить повторение

Галочка «повторяется» в карточке задачи. Сняла, задача стала обычной:

```
срок          подставляется конец текущего спринта
спринт        текущий
статус        в плане, если сегодня не отмечена, иначе сделано
отметки       сохраняются в истории, видны в журнале
```

### Правила привязки

| Тип задачи | Человек | Проект |
|---|---|---|
| по лиду | есть | не нужен, у лида проекта нет |
| по клиенту | есть | **обязателен**: один подставляется молча, из нескольких выбор |
| внутренняя | нет | не обязателен |
| продуктовая | нет | проект продукта |

Задача, сделанная **для** клиента, это клиентская задача, даже если это подготовка КП.
Правило: если работа существует из-за конкретного клиента и исчезнет вместе с ним,
она клиентская

### Шаблоны задач

**Готовые шаблоны, полный список**

```
следующее касание        универсальная, из любого статуса
                         срок конец следующей недели

отправить КП             подготовить и отправить
провести зум             после закрытия всплывает «следующее касание»
получить оплату          подставляет проект, сумму и срок из платежа

собрать базу             подставляет рассылку, факт по числу контактов
отправить рассылку       подставляет рассылку, факт по статусу отправлено

подготовить акт          по рефералу, подставляет период
выплатить процент        по рефералу, подставляет сумму к выплате
```

Шаблоны рассылки и реферала создаются парами и описаны в своих разделах

У «Собрать базу» и «Отправить рассылку» обязательна действительная
рассылка того же направления. Без выбора сервер возвращает 422,
`oshibka: nuzhna_rassylka`, `pole: rassylka_id`, не создавая задачу,
историю, состав или подтверждение. Каталог отмечает оба шаблона
`nuzhna_rassylka: true`; `tip=rassylka` выбирает эти заготовки.
Сбор базы предлагает список действующих рассылок направления;
факт равен действительному числу контактов, включая известный ноль.
Шаблон не подставляет календарный срок рассылке.

На телефоне выбор типа «рассылка» открывает снизу две кнопки:
«новая рассылка» и «к существующей», каждая не ниже44px.
Свайп вниз по ручке закрывает выбор: тип и введённый текст остаются,
вариант рассылки пуст, сохранение заблокировано, запрос не отправляется.
Повторное открытие доступно из формы. После неизвестного ответа
проверка сохранения читает прежний запрос; повтор не выполняется сам.
Черновик сбора базы тоже сохраняет поля и выбранную кампанию;
после перезагрузки список перечитывается перед созданием.


### Шаблоны правятся в Полезном

Вкладка «Шаблоны» в Полезном

```
Шаблоны задач                                   + создать шаблон

[следующее касание] [отправить КП] [провести зум] [получить оплату]
[собрать базу] [отправить рассылку] [подготовить акт] [выплатить процент]
[мой: разбор недели] [мой: созвон с подрядчиком]
```

Нажала на чип, открылась карточка шаблона: те же поля, что у задачи
Правится, удаляется, дублируется

**Когда шаблонов нет**, вместо чипов текст «своих шаблонов пока нет»
и кнопка «создать шаблон» справа

**Создание из задачи.** В карточке задачи кнопка «сохранить как шаблон»
Шаблон хранит название, описание, тип, подзадачи, срок по умолчанию
Не хранит человека, проект, ответственного

**Чьи шаблоны видно.** Готовые видят все. Свой шаблон по умолчанию
только мой, галочкой открывается команде

**Удаление шаблона** не трогает созданные по нему задачи

Создание и правка своего шаблона сохраняют массив `podzadachi` целиком,
в указанном порядке и в одной транзакции с полями шаблона. Пустой массив
при правке удаляет шаги только из шаблона. Прежние задачи самостоятельны
Срок задаётся числом календарных дней, концом текущей или следующей недели. Встроенное «следующее касание» всегда предлагает конец следующей недели, включая переход года; его своя копия сохраняет это правило. Автор берётся из проверенной сессии. Свой шаблон по умолчанию личный;
читать и применять чужой можно только после открытия команде. Правит
и удаляет свой автор; общий шаблон отключённого автора доступен для правки администратору. Готовый можно только читать и дублировать себе

Своя копия шаблона сохраняет правило подсчёта. У шаблонов с фактом
«число контактов» или «отправлено» тоже обязательна рассылка.
Каталог отдаёт `rol_rassylki` и `nuzhna_rassylka`; фильтр `tip=rassylka`
показывает и такие свои заготовки с обычными правилами приватности.
Задача при создании сохраняет функцию в существующем `rol_v_rassylke`:
`sobrat_bazu` или `otpravit`. Она считает факт по этому собственному
правилу и после правки или удаления шаблона. `shablon` сохраняет
происхождение, а редактирование шаблона не переписывает задачи.
Сбор базы не создаёт состав отправки и не попадает в список волн.

У своей отправки новой кампании сохраняются исходный шаблон,
название и личность задачи при запуске первой волны. Плановая первая
отправка определяется профилем кампании и отсутствием состава;
её явный общий план правится вместе с кампанией до запуска.
После запуска новая волна имеет свой состав и план, а первоначальный
общий план сохраняется. Редактирование или удаление шаблона не
подменяет функцию и происхождение уже созданных задач.

Форма передаёт явно выбранную функцию. Если правило шаблона
изменилось за время заполнения, сервер отказывает без частичной
задачи и кампании. Введённые поля остаются в сыром черновике;
после перезагрузки сравнение показывает старый и новый подсчёт.
Повторное применение текущего шаблона и выбор режима выполняются
явно. Удалённый или чужой личный шаблон нельзя применить новым
запросом; прежнее подтверждённое создание проверяется своим ключом
и после удаления шаблона, без новой записи. При сохранении задачи
или набранной формы как шаблона остаётся способ подсчёта, не остаются
кампания, человек, проект и ответственный. Старые null и volna
в рабочих строках не переписываются.


POST /api/shablony принимает необязательный UUID `zapros_kljuch`,
GET /api/shablony?zapros_kljuch=UUID проверяет только своё добавление,
POST с `otmenit_dobavlenie: true` резервирует неиспользованный ключ
После неизвестного ответа и перезагрузки сначала выполняется чтение;
повтор возможен только явно, с тем же ключом и сохранённым телом
Дублирование и сохранение из задачи принимают тот же ключ, проверяются
общим GET. Правка использует прочитанную версию, включая список шагов;
прямое изменение шагов в базе тоже меняет версию родителя. Удаление
с подтверждением передаёт прочитанную версию и не затрагивает задачи

**Дублирование задачи.** В карточке кнопка «дублировать»: копия с тем же содержимым, человек и проект очищаются

Срок по умолчанию у «следующего касания»: через месяц при стадии «не сейчас»,
в остальных случаях конец следующей недели

### Анимация при действии

При закрытии задачи и при переводе лида в клиента показывается анимация:
выезжает картинка. Это отметка, что действие прошло
