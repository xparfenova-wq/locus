**Правила именования**

```
транслит              как таблицы в схеме, без английского
множественное число   ljudi, zadachi, не chelovek

действие последним    /api/sotrudnichestva/12/arhiv
```

Ручек, которых нет в этом списке, быть не должно. Появилась новая,
сначала сюда, потом в код

**Методы: что каким запросом делается**

Операция задаётся методом, а не полем в теле. Никаких полей вроде `operacija`
внутри запроса

```
GET     /api/zadachi            список с фильтрами в строке запроса
GET     /api/zadachi/4827       одна задача
POST    /api/zadachi            создать, тело без id, сервер выдаст номер
PATCH   /api/zadachi/4827       изменить переданные поля, остальные не трогать
DELETE  /api/zadachi/4827       выставить udaleno: да, строку не удалять
```

PATCH меняет только то, что пришло в теле. Поле, которого в теле нет,
остаётся как было. Поля `id`, `sozdano`, `kto_dobavil` в теле PATCH дают 400

**Подручки: действия, которые не укладываются в четыре метода**

Имя действия идёт последним, транслитом

```
POST /api/zadachi/iz_shablona          создать задачу из шаблона
POST /api/zadachi/4827/dubl            скопировать задачу
POST /api/zadachi/4827/vernut         вернуть из корзины
GET  /api/zadachi/4827/korzina        проверить состояние и отметки, включая корзину
POST /api/shablony/iz_zadachi          сделать шаблон из задачи
POST /api/shablony/tpl_12/dubl         скопировать шаблон
POST /api/sotrudnichestva/12/arhiv     убрать в архив и вернуть
```

Новая волна остаётся обычной задачей со своим планом. Действие
`POST /api/rassylki/{id}/volna` проверяет выбранных получателей и создаёт
эту задачу одной транзакцией. Отдельной пользовательской сущности волны
нет. Внутренний снимок хранит её состав; последняя связь человека
с задачей не заменяет список участников прежних волн.

**Связанные записи при создании задачи**

Форма создания собирает задачу целиком, вместе с подзадачами,
участниками и прикреплёнными материалами. Три поля в теле
`POST /api/zadachi` не колонки задачи, а связанные записи,
которые ручка раскладывает по своим таблицам одной транзакцией:

```
podzadachi   список  [{nazvanie, otvetstvennyj?, srok?}]
             создаются задачами того же направления и типа
             с roditel_id = новая задача
uchastniki   список  ["login", …] или [id, …]
             ложатся в zadacha_uchastniki
materialy    список  [{nazvanie, ssylka}]
             ложатся в materialy с zadacha_id = новая задача
```

Пустой список равнозначен отсутствию поля. Если хоть одна
связанная запись не легла, не создаётся ничего: иначе человек
видит задачу без файла, который он прикрепил, и не понимает,
потерялся файл или не прикрепился

**Связанные записи при создании человека**

`POST /api/ljudi` принимает вместе с полями человека:

```
kontakty          [{tip, znachenie, osnovnoj?, porjadok?}]
sotrudnichestvo   {napravlenie, rol, istochnik?, istochnik_tekst?,
                   rekomendoval_id?, kontekst?, osobennosti?}
kontakt_dlja      {sotrudnichestvo_id, versija}
```

Контакты и сотрудничество создаются тому же человеку. `kontakt_dlja`
передаётся из поля контакта по направлению: признак нового человека
по умолчанию `kontaktnoe_lico`, а `kontakt_id` выбранного сотрудничества
меняется с проверкой увиденной версии. Собственное сотрудничество
в таком запросе не создаётся. Без этого контекста признак по умолчанию
`sobstvennyj`. Ошибка контакта, связи или конфликт версии откатывает
человека, все связанные записи, журнал и версии целиком. При конфликте
форма сохраняет введённый текст и предлагает явный выбор

Ручной перевод контактного лица в собственного через
`PATCH /api/ljudi/{id}` создаёт одно сотрудничество с ролью `lid`
в выбранном направлении. Поле запроса `napravlenie_lida` задаёт это
направление и не хранится колонкой человека. Если оно не передано,
берётся единственное направление действующих сотрудничеств,
где человек указан контактом. При отсутствии единственного направления
сервер просит выбрать его, ничего не меняя. Признак, новое сотрудничество,
журнал и версии сохраняются одной транзакцией

Для справочников и выбора контакта `GET /api/ljudi?vse_roli=1` включает
обе роли. Обычный список исключает контактных лиц до подсчёта и пагинации;
чип передаёт `rol_v_baze=kontaktnoe_lico`. В этом режиме фильтр направления
использует связи `sotrudnichestva.kontakt_id`.

При создании рассылки из текущей выборки
`POST /api/ljudi/rassylka_iz_nabora` принимает либо
`nabor_filtrov_id`, либо `filtry` вместе с названием и направлением
Во втором случае личный набор фильтров, рассылка, её участники и задача
первой волны сохраняются одной транзакцией. Ошибка не оставляет
частичного результата. Отбор использует те же фильтры и поиск, что список Людей, без ограничения одной страницей. Неизвестные условия
отклоняются; контактные лица, архив и команда не включаются
Личный набор другого участника доступен только после открытия команде

`/api/zadachi/4827/otmetki` только по одной

Для К-148 вложенный адрес `POST /api/okr/vehi/{id}/zadachi` создаёт задачу
из конкретной вехи через общий слой задач: с версией, журналом, проверкой
ответственного и связей. Это точное исключение из обычной глубины адресов;
произвольные дополнительные сегменты по-прежнему недоступны

Ответ подручки такой же, как у POST на саму таблицу: созданная или изменённая строка целиком

`GET /api/akkaunty/{id}/pokazatel?metrika=podpischikov` показывает
предпросмотр одной из восьми метрик тем же расчётом, что результат ОКР.
Ответ: akkaunt_id, metrika, znachenie и obnovleno. Если замера нет,
znachenie равно null; это не ноль и не начальное число результата

`GET /api/akkaunty/{id}/metriki` сохраняет список снимков в spisok и дополнительно возвращает metriki: восемь показателей с числом и настоящей
датой измерения; po_publikacijam содержит расчёты по публикациям. Карточка,
предпросмотр и ОКР используют этот серверный расчёт. Медиана и вовлечённость
берут последние 30 календарных дней по Москве, включая сегодняшний
У вовлечённости показывается, по скольким из всех публикаций периода она
считалась; это отношение сумм реакций и просмотров по одним и тем же публикациям с известными числами. Повторный сбор за день уточняет одну
строку. Непереданное поле сохраняет число и прежнюю дату; null отклоняется

Сборщик использует один внутренний ключ LOCUS_KLJUCH_SBORA в заголовке
x-locus-sborschik. Ключ не даёт доступ к людям, задачам, деньгам, файлам
или правам. GET /api/akkaunty для сборщика возвращает только активные
аккаунты, параметры сбора и отпечаток их привязки. Изменившаяся привязка
не позволяет записать результат, полученный от прежнего аккаунта

POST /api/akkaunty/{id}/prinjat_sbor принимает одним пакетом снимок,
публикации, их дневные измерения и результат запуска. Ошибка любой части
откатывает весь пакет. У пакета есть kljuch_zapuska: повтор после сетевого
сбоя возвращает прежний результат без дублей; тот же ключ с другим
содержимым даёт409. Отложенные пакеты сохраняются сборщиком до подтверждения
сервера. sobrat остаётся действием участника: создаёт один ожидающий запуск,
даже при повторном нажатии; служба подбирает его в течение пяти минут

## Ссылка на любую сущность

У каждой сущности есть адрес, по которому она открывается, и кнопка
«скопировать ссылку»

```
задача        locus.oreshkin.me/synapt/4827
подзадача     locus.oreshkin.me/synapt/4827#p12
человек       locus.oreshkin.me/ljudi/212
проект        locus.oreshkin.me/proekty/48
рассылка      locus.oreshkin.me/rassylki/7
цель          locus.oreshkin.me/okr/15
направление   locus.oreshkin.me/synapt
```

**Первым в адресе идёт направление**, потом короткий номер. Так по ссылке
видно, к чему она относится, не открывая

Номер короткий и не по порядку создания: 4827, а не 1, 2, 3. По номеру
нельзя понять, сколько у нас задач

**Кнопка «скопировать ссылку»** в карточке каждой сущности, рядом
с заголовком. Нажала, в буфере адрес, внизу тост «ссылка скопирована»

Отдельные элементы интерфейса ссылок не имеют: на кнопку или плашку
сослаться нельзя, и это нормально

## Сообщить об ошибке

В шапке, рядом с колокольчиком, кнопка «что-то сломалось»

```
Что сломалось

[ опиши, что произошло                    ]

приложится автоматически:
  экран, на котором ты была
  что нажимала последним
  текст ошибки, если он был

          отправить            отмена
```

Отправленное уходит двумя путями сразу:

```
в Telegram администратору     сообщение с текстом и экраном
на сервер            в журнал ошибок, с полным контекстом
```

**Журнал ошибок** лежит на сервере файлом, не в базе Локуса: если сломалась
база, журнал должен выжить. Я читаю его напрямую и чиню

**Ошибки без участия человека** пишутся туда же сами: страница не загрузилась, запрос отдал пятисотую, скрипт упал. С тем же контекстом

## Воронка

Отдельный блок в планёрке и в направлении:

```
Воронка Synapt, квартал

лиды         47
клиенты      12        26% от лидов
проекты      18
оплачено     9         50% от проектов
```

Считается по журналу изменений: когда сотрудничество меняло роль
Поэтому без журнала воронка не работает

# ЧАСТЬ III-А. АДРЕСА СТРАНИЦ

## Правило

**Любое состояние, которое можно показать, имеет адрес.** Открыл карточку,
адрес в строке поменялся. Скопировал, отправил, человек попал туда же В первой версии Локуса ссылки были не у всего, и каждый раз приходилось
объяснять словами, куда зайти. Это закрывается здесь

## Схема

Короткий номер, а не название: название меняется, ссылка ломается

```
/synapt/4827             задача 4827, направление первым
/synapt/4827#p12         подзадача
/ljudi/212               человек
/proekty/48              проект
/rassylki/7              рассылка
/okr/15                  цель
/synapt                  направление
/synapt/zadachi          задачи направления
/synapt/kontent          контент-план
/synapt/strategija       стратегия направления
/planerka/media?nedelja=43   планёрка Медиа, неделя 43
/okr?period=2026-q4      ОКР на квартал
/moe                     моё пространство
/kabinet                 личный кабинет
/poleznoe/lenta          вкладка Полезного
/poisk                   поиск по всему Локусу, отдельная страница
/poisk?chto=клиент А      поиск с готовым запросом
/poisk?chto=клиент А&tip=zadacha   поиск, отобранный по типу
/ljudi?rassylka=2        Люди, отобранные по рассылке
/ljudi?rassylka=2&status_rassylki=otvetil   плюс статус в рассылке
/ljudi?stadija=v_rabote  Люди, отобранные по стадии
```

**Поиск это отдельная страница, а не только слой поверх экрана.**
Палитра по Cmd+K при этом остаётся: она для тех, кто
знает, что ищет, страница – чтобы смотреть выдачу целиком,
группами по типам, с отбором и ссылкой на конкретный результат

**Направление идёт первым в адресе задачи.** Так по ссылке видно, к чему
она относится, не открывая

Задача сменила направление: адрес стал новым, а старая ссылка отвечает
перенаправлением на него, а не ошибкой. Номер задачи уникален во всём
Локусе, направление в адресе это подсказка человеку, а не часть ключа

## Что ещё получает адрес

```
фильтры в списке       /zadachi?napravlenie=media&status=v_processe
открытая подзадача     /synapt/4827#p12, она же полноценная задача
комментарий            /synapt/4827#k-77, прокрутка к нити
секция истории         /ljudi/212#istorija
```

## Кнопка «скопировать ссылку»

**Не на каждом состоянии, а на каждой карточке и экране**

```
есть кнопка      карточка задачи, человека, проекта, цели
                 экран направления, планёрки, контент-плана
                 страница Полезного

нет кнопки       попапы подтверждения, тосты, подсказки
                 открытый фильтр, раскрытый аккордеон
```

Правило: кнопка там, где человеку есть что показать другому. Адрес при этом
меняется всегда, даже там, где кнопки нет, чтобы можно было скопировать
из адресной строки

Один клик, ссылка в буфере, тост «Ссылка скопирована»

Без кнопки люди копируют из адресной строки, а на телефоне это неудобно

## Заголовок вкладки браузера

Название сущности первым, Локус вторым: «Отрисовать баннеры, Локус»
Иначе десяток открытых вкладок выглядит одинаково

Результаты сгруппированы по типу, **до пяти на группу**. Группы в порядке:

Совпадение подсвечено в тексте

До создания видно, что система поняла, и это можно поправить

# ЧАСТЬ V. СОХРАННОСТЬ ДАННЫХ

Подтверждённая запись должна сохраняться надёжно. При неизвестном исходе интерфейс сохраняет черновик и проверяет результат перед повтором.

## Чтобы ничего не терялось

**1. Автосохранение.** Ввёл и ушёл, сохранилось само. Никаких кнопок «сохранить» на каждом шаге

**2. Черновик не теряется.** Закрыл окно, пропал интернет, текст остался. Вернулся, он на месте

**3. Сохраняем максимум, о несохранённом сообщаем явно.** Если имя сохранилось,
а телефон нет, на экране видно, что именно не прошло. Молчать нельзя

**4. Успешный ответ только при реальном успехе.** Сейчас в старом коде ошибка иногда
приходит с кодом 200, интерфейс радуется, а в базе ничего нет. Это и есть причина
пропавших данных

**5. Журнал изменений.** Кто, что, когда, старое значение и новое. Если данные пропали,
видно, где именно

**6. Видимое состояние записи.** Пока идёт сохранение, это видно. Если не сохранилось,
на экране ошибка, а не тишина

## Чтобы нельзя было навредить

**Вход** по личному логину и паролю, пароль хранится хешем, не текстом

**Предохранитель правильной стороной:** отсутствие настройки закрывает доступ, а не открывает
Эта дыра уже была найдена в старом коде

**Внутренний ключ** для служебных вызовов отдельно от человека входа

**Удаление помечает, а не стирает.** Запись уходит с экрана, но лежит в базе

**Отмена последнего действия.** Любая правка возвращает ключ отмены, в углу на 10 секунд
плашка «Стадия изменена, отменить»

**Массовые операции** пишутся в журнал и отменяются всегда

## Бэкап

Снимок базы перед каждым переносом, с датой в имени

Ежесуточный бэкап и **проверка восстановлением**: восстановить в сторону и посчитать записи
Файл бэкапа это признак, а не факт

Кнопка возврата на старую базу держится месяц после переключения

## Одновременная работа десяти человек

SQLite в режиме WAL с таймаутом ожидания, иначе «база занята» на ровном месте

**Версия записи.** У каждой правимой таблицы поле `versija`: целое,
растёт при каждой записи. Ответ сервера всегда его содержит, PATCH
обязан его прислать. При устаревшей версии проверяется, какие именно поля
изменились. Независимые поля сохраняются оба, как требует К-1672
Если то же поле уже изменили, приходит отказ с текущим значением,
известным автором и временем. Правка не применяется, свой текст остаётся
в поле. Можно явно загрузить сохранённое или подтвердить свой вариант;
следующая чужая правка снова вызывает конфликт. Вернувшееся к прежнему
значению поле тоже считается изменённым. Служебный учёт версий полей
атомарен с записью и недоступен как предметный API; история до его внедрения не угадывается

Смена статуса, закрытие и отмена в интерфейсе используют версию показанной
строки или ответ своего сохранения. Запросить свежую версию перед записью
и тем самым скрыть конфликт нельзя. POST закрытия проверяет переданную
`versija` до изменения родителя и подзадач. Для прежних внешних клиентов
параметр этого POST остаётся необязательным; рабочий интерфейс передаёт его всегда. Сбой чтения после успешной записи сообщается как сохранённое изменение
с неудавшимся обновлением списка, без повторной записи

У повтора сохраняется выбранный день. Отметка за прошлый день не подменяется
сегодняшней, а будущая неделя не позволяет отметить сегодня вместо будущего
Строки, статусный фильтр, сводка и числа планёрки используют один контекст дня
для вычисляемого статуса повтора. Обычная отметка с кружка выполняется одним
бизнес-запросом без предварительного чтения карточки

Открытая страница обновляется опросом раз в 30 секунд. Это значит, что экран
отстаёт от базы максимум на 30 секунд, и при приёмке числа сверяются после
обновления страницы

Пока открыто меню или окно, человек вводит текст либо ещё идёт сохранение,
опрос не перерисовывает текущий интерфейс. После окончания действия опрос
возобновляется

Живой правки чужими руками на экране не видно: если администратор переименовала
задачу, пока редактор А смотрит на неё, редактор А увидит новое название в течение
30 секунд, без тоста. Тост показывается только тому, кто сам правил это же поле (см. одновременную правку выше)

# ЧАСТЬ V-А. КОГДА ЧТО-ТО СЛОМАЛОСЬ

## Что уже работает

Сторож `locus-watch.sh` стоит на сервере и проверяет каждые пять минут:

```
находится ли адрес в интернете     проверка DNS
открывается ли страница            код ответа 200
жива ли служба                     systemctl is-active
```

Нашёл проблему, пишет администратору в Telegram один раз, а не каждые пять минут
Служба перезапускается сама при падении (`Restart=always`)

Снимок базы делается каждые 10 минут, ночной бэкап в 3 часа

## Что добавляем

### Проверка не только страницы, но и данных

Сейчас сторож видит, что страница открылась. Этого мало: страница может
открыться, а данные не отдаться

```
добавляем     запрос к API за числом задач текущей недели
              если ответ не число или ошибка, это поломка
```

### Автопочинка в три шага

```
1. служба упала          перезапуск, уже работает
2. служба жива, API мёртв  перезапуск службы, один раз
3. не помогло              откат на последний снимок базы
                           и сообщение администратору: «откатил на снимок 14:30»
```

Третий шаг делается только с подтверждением: сторож пишет
«база не отвечает, откатить на снимок 14:30?» и ждёт ответа в боте

**Почему не автоматом:** откат теряет работу с момента снимка
Это решение человека

### Техническая диагностика

Блок «Платформа» в личном кабинете отменён администратором в позднем разборе интерфейса
28 октября. Не возвращать его по раннему описанию. Пять фактов остаются
доступны технической диагностике через защищённый GET /api/sostojanie:

```
служба            работает, запущена 3 дня назад
последний снимок  10 минут назад
ночной бэкап      сегодня 03:00, проверен восстановлением
место на диске    4 ГБ свободно
ошибки за сутки   0
```

# ЧАСТЬ V-Б. МИГРАЦИИ СХЕМЫ

Структура базы будет меняться после запуска. Чтобы менять её, не ломая
данные, все изменения идут пронумерованными файлами

```
migrations/
  001_pervaja_shema.sql
  002_pole_slozhnost.sql
  003_tablica_grafik.sql
```

**Как работает:** система хранит номер последней применённой миграции
При запуске накатывает только новые

**Правила:**

```
миграции не правятся задним числом, только новые поверх
каждая миграция имеет обратную, для отката
перед накатом снимок базы
накат сначала на копии, потом на боевой
```

**Что нельзя делать без отдельного решения:**

```
удалять колонку с данными
менять тип поля, если в нём уже есть данные
переименовывать таблицу
```

Такие изменения делаются в три шага: добавить новое, перенести данные,
удалить старое отдельной миграцией через неделю

# ЧАСТЬ VI. КОНТРАКТ API

Пять дыр, найденных 17 октября, это отсутствие спецификации, а не баги реализации

## Жёсткие правила

**1. Правятся только переданные поля.** Правка имени не затирает телефон, почту и заметку
Раньше запрос перечислял все колонки и молча обнулял непереданные

**2. Справочники проверяются.** Направление и статус сверяются со списком, а не принимаются
любой строкой

**3. Чужой идентификатор не перезаписывает чужую карточку**

**4. Код 200 только при успехе.** На ошибке честный код ошибки

**5. Автор обязателен у всех записывающих вызовов**, иначе журнал недостоверен

### Вход для агентов

У каждого человека свой логин и пароль. У Клода каждого человека свой ключ, привязанный
к этому человеку

В журнале это видно: «редактор А закрыл задачу» или «Клод редактора А закрыл задачу»
Разница важна, когда разбираешь, откуда взялась запись

Технически это одна колонка в журнале: кто и чем. Делается сразу, потом добавить
сложнее

## API как главный вход

У всей команды есть Клод. Самый дешёвый массовый ввод это не форма, а «Клод, разбери
транскрипт зума и залей касания в Локус»

Поэтому API проектируется как главный вход, а интерфейс как один из клиентов:

# ЧАСТЬ VII. ИМПОРТ И ЭКСПОРТ

## Выгрузка

Три формата по цели:
```
CSV    таблицы для человека
JSON   для агента, со схемой
XLSX   когда надо отдать наружу
```

Выгрузка учитывает текущий фильтр: что видно на экране, то и выгружается
Отдельно кнопка «выгрузить всё»

## Загрузка

Сопоставление колонок, предпросмотр перед записью, обработка дублей: «загрузили 300 строк,
40 уже есть в базе, что с ними»

Перед записью проверка, после записи отчёт «добавлено, обновлено, пропущено»
