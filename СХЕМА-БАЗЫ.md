# Схема базы Локуса

Все таблицы и поля в одном месте. До этого они были россыпью
по критериям приёмки, теперь сведены

---

# Что такое схема базы и зачем она

База это набор таблиц. Таблица это как лист Excel: строки и колонки

```
таблица «люди»      одна строка = один человек
                    колонки: имя, телефон, город
таблица «задачи»    одна строка = одна задача
                    колонки: название, срок, кто делает
```

**Зачем сводить в один документ.** Пока таблицы описаны по кускам в разных
разделах, легко завести два поля для одного и того же или забыть связь
Схема в одном месте это то, по чему пишется код

---

# I. ЛЮДИ И ОТНОШЕНИЯ

## Пределы длины текстовых полей

Предел назван один раз здесь, критерии ссылаются на него, а не называют
своё число

```
nazvanie у задачи, проекта, рассылки, шаблона,
направления, аккаунта, услуги, результата   200 знаков
nazvanie у цели                             300 знаков
nazvanie у сохранённого набора фильтров      40 знаков
opisanie, kontekst, zametka, osobennosti   2000 знаков
pochemu_otlozheno, naznachenie              500 знаков
nomer документа, dogovor_nomer              100 знаков
procent_shkala                              300 знаков
ssylka, fajl                                500 знаков
znachenie контакта                          200 знаков
```

Пустая строка после обрезки пробелов приравнивается к незаполненному
полю: у обязательного даёт 400, у необязательного хранится как null

## Версия записи: одно правило на все таблицы

У каждой таблицы, которую правит человек, есть поле `versija`: целое
число, начинается с 1 и увеличивается на 1 при каждой записи

```
versija    число, растёт при каждом PATCH
```

**Зачем.** редактор А открыл задачу, администратор в это же время её переименовала
Без версии правка редактора А затёрла бы правку администратора молча. С версией сервер
видит, что редактор А прислал устаревшее значение, и отвечает отказом
с текущим состоянием

PATCH без `versija` в теле отдаёт 400. Устаревшая версия даёт 409,
если после неё изменили то же поле или связанную с ним часть записи
Ответ содержит текущее состояние, известного автора и время. Независимые
поля сохраняются оба, как требует К-1672; версия записи продолжает расти
Изменённое и затем возвращённое поле тоже считается изменённым. История
до внедрения учёта полей не угадывается: для неё действует отказ по версии

Поле есть у `ljudi`, `sotrudnichestva`, `proekty`, `zadachi`, `celi`,
`rezultaty`, `rassylki`, `uslugi`, `shablony`, `kontakty`, `materialy`,
`dokumenty`, `anketa`, `grafik`, `kommentarii`, `tezisy`. У журналов, замеров и снимков его нет: они
только добавляются, их никто не правит

## schetchiki_anket

Служебный счётчик версии анкеты, без ответов и других личных текстов
Сохраняется после удаления анкеты: старая вкладка не должна перезаписать
заново заполненную анкету того же человека. Обычным API не открывается
При удалении самого человека счётчик удаляется вместе с ним

```
chelovek_id          INTEGER NOT NULL REFERENCES ljudi(id) ON DELETE CASCADE
poslednjaja_versija  INTEGER NOT NULL: последняя выданная версия анкеты
CHECK (typeof(poslednjaja_versija)='integer' AND poslednjaja_versija>=1)
```

## import_svjazi

Служебное соответствие исходных и новых записей при переносе справочников
Обычным API не открывается. Старый ID сам по себе не является ID нового
человека или аккаунта. Несколько исходных записей могут ссылаться на одну
новую только после сопоставления идентичности. Имя само по себе не является
подтверждением. Роли, стадии, проекты и деньги эта таблица не переносит

```
istochnik         TEXT NOT NULL: постоянный код старой системы
tablica           TEXT NOT NULL: исходная таблица справочника
staryj_id         TEXT NOT NULL: исходный ключ строкой
chast             TEXT NOT NULL: основная запись, компания или контактное лицо
chelovek_id       INTEGER REFERENCES ljudi(id): новая запись человека, компании, канала или школы
akkaunt_id        INTEGER REFERENCES akkaunty(id): новая запись аккаунта
sha256            TEXT NOT NULL: хеш разрешённых исходных полей
ishodnye_dannye   TEXT NOT NULL: JSON только исходных полей справочника
sozdano           TEXT NOT NULL: дата и время переноса UTC
CHECK ((chelovek_id IS NOT NULL) + (akkaunt_id IS NOT NULL) = 1)
```

Первичный ключ: istochnik, tablica, staryj_id, chast. Ровно одна ссылка
заполнена. Внешние ключи не позволяют оставить соответствие без новой записи
Повтор неизменённого источника не создаёт запись снова. Изменение исходника
после переноса требует сравнения, а не автоматической перезаписи новых данных
Сырые данные содержат контакты: входят только в приватный бэкап, не в пакет ревью

## versii_polej

Служебный учёт последних версий полей для К-1672. Не предметный ресурс,
не показывается в интерфейсе и не открывается обычным API. Значения полей
не копируются. Пустой pole обозначает версию записи; `*` – границу
достоверной истории. Служебные строки обновляются в той же транзакции,
что и запись, в том числе при прямом SQL. Полный бэкап сохраняет их Внутри пишущей транзакции запись с tablica='', obekt_id=0 и pole=''
передаёт триггерам автора запроса. Она удаляется до COMMIT: другие
подключения и резервные копии её не видят

```
tablica           TEXT NOT NULL: имя защищаемой таблицы
obekt_id          INTEGER NOT NULL: её первичный ключ
pole              TEXT NOT NULL: поле, пустая строка или *
versija           INTEGER NOT NULL: последняя версия изменения
kto               INTEGER: автор, если известен
kogda             TEXT: дата и время изменения UTC
```

Первичный ключ: tablica, obekt_id, pole. Старый период до установки
учёта не получает выдуманных версий полей или авторов. Удаление предметной
строки удаляет её служебные строки. Это одна из технических таблиц сверх
53 предметных; она не вводит новую бизнес-сущность

## Логические поля: одно правило на весь Локус

Поле «да или нет» живёт в трёх видах, и это не три значения, а три
представления одного

```
в базе      1 и 0, тип INTEGER
в API       true и false
на экране   да и нет, или галочка
```

Строк «да» и «нет» в теле запроса и ответа не бывает: `udaleno: "да"`
отдаёт 400. В SQL сравнение идёт с 1 и 0: `where udaleno = 1`, а не
`where udaleno = 'да'`

`null` в теле запроса трактуется как отсутствие ключа и подставляет
значение по умолчанию. Отдельного третьего состояния у логического
поля нет

## ljudi

Один человек, одна строка. Компания тоже человек, с признаком

```
id                число, автоматически
imja              текст, обязательно
jurlico           да или нет
gorod             текст
nisha             текст
zametka           текст
komanda           да или нет: наш человек или внешний
pol               zh или m: нужен, чтобы журнал и уведомления
                  склонялись верно. «администратор поменял» читается
                  неправильно, а род по имени не угадывается
rol_v_baze        sobstvennyj или kontaktnoe_lico: сам человек
                  или сотрудник клиента, с кем общаемся
chto_eto          TEXT DEFAULT 'chelovek': chelovek, kompanija, kanal, shkola: что за сущность.
                  Канал и школа ведут себя как человек: им пишут,
                  они отвечают, второе сообщение это следующее
                  касание. Отдельной таблицы им не заводим
arhiv             да или нет: человек ушёл целиком, все его
                  сотрудничества перестают считаться
arhiv_s           дата ухода в архив
vozvrat_s         TEXT: день последнего возврата из архива по Москве, исторические неизвестные даты не выдумываются
aktiven           да или нет: для ухода из команды
imja_norm         имя в нижнем регистре, ё приведена к е, для поиска
                  и защиты от дублей. Считается сервером из imja
foto              путь к файлу, необязательно: если пусто, кружок
                  рисуется по inicialy и cvet
inicialy          текст, 2 буквы для кружка
cvet              текст, #hex для кружка
dostup            polnyj или bez_deneg: что человек видит в Локусе
sozdano           дата
```

**Поля `rol` у человека нет.** Роль это про сотрудничество, а не про
человека: один и тот же человек бывает клиентом по одному направлению
и рефералом по другому. Роль живёт в `sotrudnichestva.rol`, а то, что человек видит в Локусе, называется `dostup`

**Поля `onbording` нет.** Прохождение не отмечается флагом у человека:
отметки шагов и подсказок лежат в `nastrojki.pokazannye_podskazki`

## kontakty

Контакт это строка. Строк у человека столько, сколько нужно: два телефона
и три почты это пять строк

Контактов у человека несколько, поэтому отдельная таблица

```
id
chelovek_id       ссылка на ljudi
tip               telegram, telefon, pochta, sajt, instagram,
                  youtube, vk, linkedin, drugoe: девять видов
znachenie         текст
osnovnoj          да или нет
porjadok          число: в каком порядке показывать строки
znachenie_norm    значение без форматирования: у телефона только
                  цифры, у почты нижний регистр. Для поиска
                  и защиты от дублей, считается сервером
```

**Зачем znachenie_norm:** телефон +7 (999) 123-45-67 и 89991234567 это один
номер. В этом поле лежат только цифры, по нему идёт проверка дублей
Второго поля нормализации нет: два хранилища одной величины разъехались бы С 15 ноября 2026 миграция 110 и декларативные правила базы запрещают
повтор (chelovek_id, tip, znachenie_norm) при непустой нормализации
Это один контакт одного человека; совпадения у разных людей этим
ограничением не объединяются. Исторические строки с пустой нормализацией
сохраняются без изменения исходного значения

Миграция 114 и декларативные правила разрешают не больше одного
osnovnoj=true для пары (chelovek_id, tip). Переключение метки выполняется
в одной транзакции. Старые неоднозначные метки останавливают обновление,
автоматического выбора или удаления контактов нет. API возвращает
osnovnoj_kontekst, отпечаток состава группы и истории основных меток
PATCH основной метки требует этот прочитанный контекст вместе с версией
строки. Изменение значения или порядка само по себе контекст не меняет

Миграция 115 согласует ключ сравнения с явным международным плюсом:
ведущая 8 в номере с плюсом сохраняется, а местная российская восьмёрка
без плюса по-прежнему сравнивается с +7. У однозначных ASCII-номеров
исправляется только znachenie_norm. Исходный текст, связи, порядок,
основная метка, версии и история полей сохраняются. Коллизия ключей
останавливает всю миграцию без объединения или удаления строк
Исторический некорректный текст автоматически не переосмысляется

Маска и страна ввода не добавляют колонок: хранится международное
znachenie, pokaz рассчитывается по общему справочнику. Параметры strana
и bez_maski относятся к вводу и не являются полями строки контакта

## sotrudnichestva

Человек плюс направление. У одного человека их может быть несколько

```
id
chelovek_id       ссылка на ljudi
napravlenie       synapt, automy, automy_junior, media, nastavnichestvo,
                  platforma, anton, assist: восемь направлений, как
                  в ТЗ. У anton признака клиентов нет
rol               lid, klient, referal: кем человек приходится
                  по этому направлению. Два сотрудничества с одной
                  ролью по одному направлению запрещены
stadija           ne_pisali, napisali, na_soglasovanii, zhdem_oplatu,
                  ne_sejchas (у лида)
                  v_rabote, zhdem_oplatu, na_soglasovanii,
                  zhdem_obratnuju_svjaz, zaplanirovan_zum, pauza (у клиента)
                  prismatrivaemsja, dogovarivaemsja, rabotaem,
                  k_vyplate (у реферала)
                  плюс своя стадия у любой роли
svoja_stadija     текст: разовая стадия только этого сотрудничества,
                  в справочник не попадает. Заполнено либо stadija,
                  либо svoja_stadija, не оба
procent           у реферала: число от 0 до 100, для расчёта
procent_shkala    текст шкалы, если процент ступенчатый: 14/9/6
                  заполнено одно из двух, число ведущее
nalog             do_vycheta или posle_vycheta: считать процент
                  до удержания налога или после
privodit_klientov да или нет: у клиентского сотрудничества признак,
                  что этот клиент приводит других. Ставится только
                  при rol = klient, у лида и реферала запрещён
vyplacheno        у реферала: сумма уже выплаченного, вносится руками
dogovor_nomer     номер и дата договора
dogovor_id        ссылка на dokumenty: сам договор
kontakt_id        ссылка на ljudi: с кем общаемся по этому направлению,
                  если не сам человек
kontekst          текст: что знаем про это сотрудничество
kommentarij       текст к текущей стадии. При смене стадии прежний
                  уходит в журнал, а не затирается
osobennosti       текст: постоянное про этого человека, не про стадию.
                  «Решения принимает только Дмитрий Владимирович»
istochnik         rekomendacija, rassylka, meroprijatie, sajt,
                  socseti, holodnyj_kontakt, svoj: откуда пришёл.
                  У rekomendacija обязателен rekomendoval_id,
                  у rassylka rassylka_id, у meroprijatie текст
                  в istochnik_tekst, у svoj тоже текст
istochnik_tekst   текст: какое мероприятие или свой источник
rekomendoval_id   ссылка на ljudi, если istochnik = rekomendacija
rassylka_id       ссылка на rassylki, если istochnik = rassylka. REFERENCES rassylki(id)
poslednjaja_zadacha дата последней закрытой задачи по этому
                  сотрудничеству. Считается сама, руками не вводится.
                  Это факт работы, а не факт разговора
poslednee_obshenie дата последнего живого общения: звонок, встреча,
                  переписка. Ставится руками кнопкой «отметить общение»
                  или ботом из Телеграма. Сама не считается: закрытая
                  задача не значит, что с человеком говорили
arhiv             да или нет: признак, роль при этом сохраняется
arhiv_s           дата последнего ухода в архив, пусто если не в архиве
vozvrat_s         дата последнего возврата из архива. Нужна планёрке
                  прошлых недель: по ней видно, что на той неделе
                  человек уже работал, хотя сейчас не в архиве
sozdano           дата
```

**Считается, в базе не хранится**

```
privedeno    людей, где istochnik = rekomendacija
             и rekomendoval_id = этот человек
zarabotano   сумма оплаченных счетов по проектам приведённых
k_vyplate    zarabotano × procent / 100 − vyplacheno
             не считается, если заполнена procent_shkala:
             там сумму считает человек
```


## fokus_sessii

Отрезки сфокусированной работы

```
id
chelovek_id       ссылка на ljudi
zadacha_id        ссылка на zadachi, может быть пустой
rezhim            fokus, pereryv, dolgij_pereryv
nachalo           время старта
konec             время завершения, пусто если прервана
zachtena          да или нет: true только если доведена до конца
pauza_s TEXT: начало текущей паузы UTC, пусто когда таймер идёт
pauza_ms INTEGER NOT NULL DEFAULT 0: накопленные завершённые паузы, целые миллисекунды
versija INTEGER NOT NULL DEFAULT 1: версия состояния таймера
identifikator TEXT: UUID экземпляра; у старых записей неизвестен до явного действия
```

Прерванная сессия хранится, но в счётчики не идёт: так видно, сколько раз
человек начинал и бросал, если это кому-то понадобится

# II. РАССЫЛКИ

## bazy

База рассылок: именованный набор людей со своим путём. Живёт дольше
одной рассылки, по ней идут волны

```
id
nazvanie          текст
napravlenie       чьё направление
opisanie          зачем эта база, текст
chto_vnutri       chelovek, kompanija, kanal, shkola: кого собираем
kto_vedet         ссылка на ljudi
arhiv             да или нет
sozdano
```

Ключ: id

## bazy_statusy

Свои статусы базы. Набор задаётся при создании и правится потом,
как свои стадии направления

```
id
baza_id           ссылка на bazy
nazvanie          своё слово: «получил доступ», «созвон»
rol               v_rabote, otkliknulsja, soglasilsja, otkaz
porjadok          число: ступень воронки
```

**Зачем роль.** Воронка и формулы ОКР не знают частных слов базы
Статус «получил доступ» с ролью `soglasilsja` попадает в цель
«5 волонтёров» без отдельной настройки. Статус без роли живёт,
но в воронку и ОКР не идёт

Ключ: id. Порядок внутри базы уникален

## bazy_ljudi

Человек в базе. Пятнадцать общих полей, по ним система считает

```
id
baza_id           ссылка на bazy
kto               ссылка на ljudi: кому пишем
kontakt           ссылка на ljudi: с кем говорим, если это не сам kto
kanal_svjazi      mail, tg, instagram, telefon
adres             почта, ник, номер
kanal_zapasnoj    второй способ связи
kontekst          что знаем про него, своими словами
kontekst_otkuda   откуда контекст: ссылка или файл
soobshenie        текст первого письма
soobshenie_vdogon текст напоминания
status_id         ссылка на bazy_statusy
segment           крупное деление базы
kogorta           мелкое деление внутри сегмента
kommentarij       заметка для своих
ssylka            адрес, куда ведём
svoi              текст JSON: свободный хвост парами имя-значение
sozdano
```

**Материалы отдельной таблицей нет:** вложения человека уже лежат
в `materialy` со ссылкой на человека, второй механизм не нужен

**Почему `svoi` текстом JSON, а не таблицей пар.** По хвосту
не считают и не фильтруют, он только показывается и уезжает
в выгрузку. Таблица пар дала бы джойн на каждую строку списка
ради данных, которые читают глазами

Ключ: id. Один человек в базе один раз: `baza_id` плюс `kto` уникальны

## rassylki

Кампания рассылки. Это то, что у участницы В называлось out_camp

```

baza_id           ссылка на bazy: по какой базе идёт волна
ploshadka         pochta, telegram, instagram

segment           кому пишем, текст

status            gotovitsja, idet, pauza, zavershena
nachalo           дата
konec             дата
```

## rassylka_ljudi

Метка рассылки на человеке. Даты нужны, чтобы считать факт за неделю

Связь рассылки и человека. Ключевая таблица для твоего вопроса о повторах

```
id
rassylka_id       ссылка на rassylki
chelovek_id       ссылка на ljudi
status            ne_otpravleno, otpravleno, otvetil, otkaz
otpravleno_at     дата
otvet_at          дата
zametka           текст: что ответил
zadacha_id        INTEGER REFERENCES zadachi(id): задача последнего общего касания.
                  Это не список участников всех волн. Состав каждой новой
                  волны хранится отдельно в uchastniki_voln.
```

**Почему дубля человека не будет.** Человек один в таблице ljudi. Если он попал в три рассылки, появятся три строки здесь, а не три человека
В карточке человека это видно чипами: «школы, отправлено», «1С, ответил»

## rassylka_kasanija

История касаний по рассылке. Нужна, чтобы считать факт каждой волны
отдельно: первая волна в факт второй не входит

```
rassylka_id
chelovek_id
zadacha_id        какая задача породила это касание
kogda             дата
chto              otpravleno, otvetil, otkaz; ne_otpravleno сброс; dobavlen добавление в кампанию
```

Статус в `rassylka_ljudi` хранится полем и обновляется одной операцией
вместе с записью касания сюда. Эта таблица история, то поле текущее
состояние: фильтр «кто молчит» по 500 людям должен работать мгновенно,
а запросом по истории он медленный


## sostavy_voln

Внутренний снимок списка получателей задачи-волны. Новые волны полные;
у прежних фиксируются только известные участники и полный состав не обещается.
Миграция оставляет таблицу пустой, не восстанавливает потерянные списки догадками.

```
zadacha_id        INTEGER NOT NULL REFERENCES zadachi(id) ON DELETE CASCADE

CHECK (polnyj IN (0,1))
```

## uchastniki_voln

Участие одного человека в каждой волне отдельно. NULL статуса у старого
участника означает, что отметки именно этой волны неизвестны. Последняя
связь rassylka_ljudi.zadacha_id не доказывает такой статус. Сброс отметки
сохраняет историю, но убирает её из текущего факта волны.

```
zadacha_id        INTEGER NOT NULL REFERENCES sostavy_voln(zadacha_id) ON DELETE CASCADE
chelovek_id       INTEGER NOT NULL REFERENCES ljudi(id)
status            TEXT: ne_otpravleno, otpravleno, otvetil, otkaz или NULL
kogda             TEXT: дата последней отметки
otschet_at        TEXT: первая действующая дата отправки волны
otvet_at          TEXT: дата действующего ответа
versija           INTEGER NOT NULL DEFAULT 1
CHECK (status IS NULL OR status IN ('ne_otpravleno','otpravleno','otvetil','otkaz'))
CHECK (versija>0)
```

## zaprosy_rassylok

Квитанции создания волн и массовых отметок, привязанные к автору и кампании.
Ключ и тело хешируются; повтор подтверждает прежнее действие. Пустой
результат резервирует отменённый ключ от позднего запроса. История
подтверждения не объявляет прежний результат текущим состоянием карточки.

```

zapros_hesh       TEXT
rezultat_json     TEXT

zadacha_id        INTEGER: созданная задача для проверки её подлинности
sobytie_id        INTEGER: запись создания задачи в журнале
CHECK (length(kljuch_hesh)=64 AND kljuch_hesh NOT GLOB '*[^0-9a-f]*')
```

### Касание

Касание это задача с типом `kasanie`: прямое общение с клиентом, а не подготовка к нему. Отдельной сущности нет, иначе пришлось бы дублировать
проект, срок и ответственного

Крепится к клиенту (`klient_id`), проект необязателен. Число касаний у клиента это сумма по всем его задачам этого типа, у проекта только по своим. Нужно для двух вещей: видеть вложенные усилия и считать, сколько
касаний прошло между стадией лида и клиентом

## zadacha_uchastniki

Участников несколько, поэтому отдельно. Стабильный id задаёт порядок
добавления. Историческое время не восстанавливается догадкой: у перенесённых
связей dobavleno пусто. Мягкое удаление задачи сохраняет связи для отмены;
физическое удаление задачи или человека удаляет их каскадом

```
id                     INTEGER, автоинкремент
zadacha_id             INTEGER NOT NULL REFERENCES zadachi(id) ON DELETE CASCADE
chelovek_id            INTEGER NOT NULL REFERENCES ljudi(id) ON DELETE CASCADE
dobavleno              TEXT DEFAULT (datetime('now')), время сервера, у старых связей неизвестно
UNIQUE (zadacha_id, chelovek_id)
```

## nerazobrannye_svjazi

Внутренний журнал старых связей, у которых нет задачи или человека
Исходные значения и их SQLite-типы сохраняются; запись не считается
активным участником и не перепривязывается автоматически. BLOB-поля без
преобразования сохраняют INTEGER, TEXT и NULL исходной записи. Время
obnaruzheno означает обнаружение при миграции, а не время старого события
Рабочего API для этой таблицы нет

```
id                     INTEGER, автоинкремент
tablica                TEXT NOT NULL
```

Снимок содержит только версию, ключ одной серверной команды,

**Поля «когда последний раз правили» в таблицах нет.** Время правки
не дублируется в самих строках: оно берётся из журнала запросом
`select max(kogda) from zhurnal where obekt = ? and obekt_id = ?`.
Второе хранилище той же даты разъехалось бы с журналом

## uvedomlenija

Уведомления пишет единый обработчик `api/sobytija-uvedomlenij.js`. Семь основных поводов
«Про меня», три повода «События», упоминание и новость; исторический тип
`podzadacha_v_moej_zadache` сохраняется для чтения старых записей. Новых событий
о создании подзадачи владельцу родителя первичное ТЗ не предусматривает
Неопознанная старая ссылка сохраняется дословно, без подбора задачи по номеру
При физическом удалении связанной записи уведомление сохраняется с пояснением

```
CHECK (tip IN ('komanda_dobavila_zadachu','komanda_dobavila_podzadachu','pomenjali_srok','dobavili_uchastnikom','vedushim_proekta','segodnja_istekaet_srok','zadacha_prosrochena','upomjanuli_v_kommentarii','kommentarij_v_zadache','zakryli_podzadachu','izmenili_zadachu_uchastnika','podzadacha_v_moej_zadache','novoe'))

CHECK (length(trim(tekst,char(9)||char(10)||char(11)||char(12)||char(13)||char(32)||char(160)||char(5760)||char(8192)||char(8193)||char(8194)||char(8195)||char(8196)||char(8197)||char(8198)||char(8199)||char(8200)||char(8201)||char(8202)||char(8232)||char(8233)||char(8239)||char(8287)||char(12288)||char(65279))) BETWEEN 1 AND 1000 AND length(tekst)<=1000 AND instr(tekst,char(0))=0)

CHECK ((zadacha_id IS NOT NULL)+(proekt_id IS NOT NULL)+(lenta_id IS NOT NULL)<=1)
CHECK (ssylka_udalena IS NULL OR ssylka_udalena IN ('zadacha','proekt','novoe'))
```

## povody_uvedomlenij

Внутренняя память событий фонового задания сроков. Ключ содержит тип,
внутренний ID задачи, её срок и точный ID получателя. Запись создаётся
атомарно с уведомлением и сохраняется после уборки прочитанного, чтобы
старую просрочку не присылать повторно. Изменение срока или ответственного
образует другой повод. Историческим уведомлениям не приписываются неизвестные
прежние сроки. Ссылка на созданное уведомление известна точно; при его уборке обнуляется,
но ключ события остаётся. Пользовательского API нет

```
kljuch                 TEXT NOT NULL: ключ события
sozdano                TEXT NOT NULL DEFAULT (datetime('now')): время сервера UTC
uvedomlenie_id         INTEGER REFERENCES uvedomlenija(id) ON DELETE SET NULL: уникальная ссылка на созданное уведомление
CHECK (length(kljuch) BETWEEN 1 AND 160)
CHECK (datetime(sozdano) IS NOT NULL)
```

## otmeny_kontaktov

Внутренние серверные квитанции отмены удаления контакта. В базе хранится
SHA256 случайного токена, участник, ID события удаления, исходная строка
и выбор основного после удаления. API не принимает исходную строку от браузера. Срок действия 30 секунд; повтор тем же участником проверяет
состояние, не создаёт вторую строку. Квитанция переживает перезапуск
Просроченные квитанции очищаются при операциях отмены и удаления
Публичного списка и общего CRUD этой таблицы нет

```

avtor                  INTEGER NOT NULL REFERENCES ljudi(id) ON DELETE CASCADE: участник удаления
do_ms                  INTEGER NOT NULL: конец окна в миллисекундах UTC
udaleno_id             INTEGER NOT NULL REFERENCES zhurnal(id) ON DELETE CASCADE: событие удаления
slepok                 TEXT NOT NULL: исходная строка контакта JSON
osnovnye               TEXT NOT NULL: ID основных контактов после удаления JSON
zapros_hesh            TEXT: SHA256 ключа одного запроса удаления, необязательно
CHECK (length(token_hesh)=64 AND token_hesh NOT GLOB '*[^0-9a-f]*')
CHECK (do_ms>0)
CHECK (json_valid(slepok))
CHECK (json_valid(osnovnye))
CHECK (zapros_hesh IS NULL OR (length(zapros_hesh)=64 AND zapros_hesh NOT GLOB '*[^0-9a-f]*'))
```

## zaprosy_zadach

Внутренняя память успешно выполненных запросов создания задач из карточки
человека. Повтор одного ключа тем же участником возвращает сохранённый
результат; другой человек или другое содержимое отклоняются. Проверка
ключа только читает результат и не создаёт задачу. Запись сохраняется

# X. ВОПРОСЫ ПО БАЗЕ, КОТОРЫЕ НАДО РЕШИТЬ

## 1. Что делать со старыми лидами без контекста

Ребята загрузят базу, по многим не будет ничего, кроме имени и телефона

**Решение:** поле `kontekst` в сотрудничестве остаётся пустым, и это
нормально. В карточке человека над этим полем стоят три подсказки
(откуда знаем, о чём говорили, когда последний раз), но поле одно

Трёх отдельных полей не заводим: заполнять три вместо одного никто
не будет, а разбирать их по отдельности мы нигде не собираемся

## 2. Последнее касание у старой базы

**Решено 23 октября:** вместо одного поля два, потому что это разные вещи
Закрытая задача не значит, что с человеком говорили: я могу неделю править
КП и ни разу ему не написать

```
poslednjaja_zadacha   дата последней закрытой задачи, считается сама
poslednee_obshenie    дата живого общения, ставится руками или ботом
```

Фильтр «давно не общались» и блок планёрки считают по `poslednee_obshenie`:
именно оно отвечает на вопрос «с кем пора связаться». По `poslednjaja_zadacha`
видно другое: работа идёт или заглохла

При загрузке старой базы `poslednee_obshenie` можно проставить датой, если
известна. Неизвестна, остаётся пустым, и человек попадает в «никогда
не общались». Это честнее, чем подставить дату задачи и решить, что контакт есть

## 3. Сколько хранить журнал

Журнал растёт быстрее всего. При восьми людях это примерно 200 записей
в неделю, 10 тысяч в год

**Предложение:** не чистить первый год, потом смотреть. 10 тысяч строк
для базы это ничто

## 4. Нужны ли файлы

Решено 22 октября: храним и файлы, и ссылки. Таблицы `materialy`
и `dokumenty`, блоки есть у человека, проекта и направления

Причина смены решения: ссылка на Google Диск умирает при смене прав
или переносе папки, а договор нужен через год

### Служебный снимок отмены создания задачи

В JSON zhurnal.srez у события создания корневой задачи может быть
otmena_sozdanija. Снимок дополняется до первого COMMIT той же команды:
корневые id и nomer, id и подтверждённые версии созданных задач,
SHA256 состояния их связей, прежние архивные флаги и даты возвращённых
людей, версии и SHA256 связанных записей. Суммы и полные строки задач
в снимок отмены не копируются. Новая отмена дополняет только этот
служебный снимок полем otmeneno: UUID команды отмены, UTC-время, автор
Исходные автор, дата, значения и контекст связей события сохраняются
Признак служит долговременной квитанцией отмены; повтор не меняет данные
Общение, просмотры и прочитанные уведомления не отменяются вместе
с созданием задачи. Рабочие записи задач удаляются мягко по общему правилу

### Техническая квитанция первоначального создания задачи

С 16 ноября 2026 otmena_sozdanija в srez исходной записи создания может
содержать zapros: format = 1, kljuch_hesh и telo_hesh. Первый хеш определяет
UUID запроса внутри автора; второй – HMAC-SHA256 канонического тела с ключом
из исходного UUID. Порядок ключей объектов не меняет намерение, порядок
элементов массивов сохраняется. В техническую квитанцию не копируются
исходный UUID, полное тело запроса, суммы или полный ответ API. Повтор читает
текущую задачу через обычные проверки доступа и использует прежний ключ
отмены. Поиск и создание квитанции входят в ту же транзакцию, что задача
и её связи. Новая таблица и изменение прежних строк для этого не требуются


### Версии направлений и архив, 16 ноября 2026
